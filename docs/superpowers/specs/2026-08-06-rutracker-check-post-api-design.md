# rutracker_check без API RuTracker: дизайн

**Дата:** 2026-08-06
**Статус:** дизайн утверждён, реализация не начата
**Предшествующий анализ:** `RUTRACKER-CHECK-ANALYSIS.md` (часть выводов исправлена, см. §3)

---

## 1. Задача

Плагин `plugins/rutracker_check` отслеживает обновление и удаление раздач и подменяет
устаревший торрент новым. Обе опоры, на которых он держался для RuTracker, отвалились:

- `api.rutracker.cc/v1/get_*` отключены (частично с 2026-03-26, полностью с середины июля 2026);
- `rutracker.org/forum/*` закрыт Cloudflare-челленджем (с ~2026-07-27).

Требуется вернуть работоспособность, не обходя защиту: только те источники, которые
RuTracker отдаёт открыто, плюс сам протокол BitTorrent.

**Охват:** только хендлер RuTracker. `nnmclub.php`, `toloka.php` и прочие не трогаем.

**Решения, зафиксированные с пользователем:**

- аккаунт обычный, не хранительский — хранительский путь (`rep.rutracker.cc`, `dl_keeper.php`) недоступен;
- подмена раздачи должна быть автоматической;
- строим полный автомат сразу, а не поэтапно.

## 2. Что проверено на живой системе

Всё ниже измерено 2026-08-06 на рабочем экземпляре пользователя, а не выведено из документации.

**Окружение:** rTorrent 0.16.19, libtorrent 0.16.19, XMLRPC API 24, 397 раздач,
из них 246 с трекером `*.t-ru.org`.

### 2.1. Детектор: `t.failed_counter` работает, `d.message` — нет

Раздачи разбиты на три группы, каждая проверена независимым запросом к трекеру
(анонс без passkey, `event=stopped`):

| Группа | Локальный признак | Вердикт трекера |
|---|---|---|
| 6 раздач | `t.failed_counter > 0` | не зарегистрированы — **6 из 6** |
| 10 раздач | `t.normal_interval = 600` | зарегистрированы — **10 из 10** |
| 8 раздач | здоровые | зарегистрированы — **8 из 8** |

Разделение без пересечений: ни одного ложного срабатывания на 18 контрольных.

`d.message` пуст у всех 246 раздач, включая шесть мёртвых. По всем 397 раздачам он
непустой лишь у пяти, и только с транспортными ошибками
(`Tracker: [Could not resolve hostname]`, `[Could not connect to server]`).
Вердикт «не зарегистрирована» в `d.message` не попадает.

**Это отменяет исходную гипотезу.** Ожидалось, что libtorrent 0.16.15+ превратит
предупреждение трекера в ошибку с текстом в `d.message`; на практике трекер отдаёт
`failure reason`, а не `warning message`, и текст до `d.message` не доходит.
Первичным сигналом становится `t.failed_counter`, а `d.message` — вторичным
дискриминатором «трекер недоступен» против «раздача снята».

### 2.2. Интервал анонса не является признаком

`normal_interval = 600` (нижняя граница клампа libtorrent) встретился у 29 раздач —
все они живы. Правило из исходного анализа («короткий интервал = мертва») дало бы
29 ложных удалений из 246. Правило отвергнуто.

### 2.3. Магнит-путь применим

`d.is_private = 0` у **всех 246** раздач RuTracker. DHT, PEX и добор метаданных
по BEP-9 разрешены. BEP-9 требует пиров, а не DHT — HTTP-трекер их отдаёт.

### 2.4. Цепочка «мёртвый хеш → новый хеш» проходит целиком

Два случая доведены до конца на реальных данных:

- топик 6880555: найден в `feed.rutracker.cc/atom/f/0.atom` с меткой `[Обновлено]`,
  оттуда получен `forum_id = 1106`, из дампа форума — новый `info_hash`, отличный от локального;
- топик 6868321: найден обходом дампов в форуме 921 («Мультсериалы»),
  `tor_status = 0`, 45 сидов, новый `info_hash`.

### 2.5. Стоимость обхода дампов подтверждена

140 форумов за 70 секунд при 6 параллельных соединениях, 50.4 МБ после распаковки.
Экстраполяция на все 1261 форумов: **около 10–11 минут**, что совпадает с оценкой,
сделанной до замера.

`feed.rutracker.cc/atom/f/0.atom` отдаёт ровно 300 записей глубиной ~9 часов,
из них 86 с меткой `[Обновлено]`. Пять из шести мёртвых топиков в это окно не попали —
фид годится как ускоритель, но не как основной источник.

### 2.6. Активные анонсы лимитируются

После примерно сорока анонсов трекер начал отвечать `403`. Это прямое подтверждение,
что активный опрос не может быть основным механизмом и должен применяться только
к кандидатам, отобранным бесплатным локальным детектором.

| Утверждение в анализе | Факт |

| «Часовой» `172.93.185.75` — признак незарегистрированного хеша | Неверно. Приходит в каждом ответе, включая зарегистрированные хеши |

| `STE_DELETED` недостижим — единственный источник это API | Верно, но `tor_status` в дампе восстанавливает признак без API |
| Вариант 2 (пробитие Cloudflare) — рабочая опция | Отвергнут на технических основаниях: стандартный solver не отдаёт бинарный `.torrent`, на форме входа картиночная капча, upstream-проект признан нерабочим |

Дополнительно: `tor_status` расшифрован по исходникам webTLO —
`0` не проверено, `1` закрыто, `2` проверено, `3` недооформлено, `4` не оформлено,
`5` повтор, `6` зарезервировано, `7` **поглощено**, `8` сомнительно, `9` проверяется,
`10` временная, `11` премодерация. Валидными считаются `{0, 2, 3, 8, 10}`.

## 4. Архитектура

Четыре слоя. Каждый следующий дороже предыдущего и вызывается только для того,
что предыдущий не смог закрыть.

```
Слой 1  локальный детект (0 запросов)      → отсеивает ~97% раздач
   ↓ кандидаты
Слой 2  подтверждение анонсом (опционально) → снимает холодный старт
   ↓ подтверждённые
Слой 3  классификация по дампу форума       → обновлена / удалена / поглощена
   ↓ обновлённые
Слой 4  добор метаданных магнитом           → байты .torrent → существующая транзакция
```

### 4.1. Слой 1 — локальный детект

Расширяем существующий `t.multicall` в `update.php:18` полями
`t.failed_counter`, `t.success_counter`, `t.activity_time_last`, `t.is_enabled`
и добавляем `d.message` в `d.multicall`.

Правило:

- `failed_counter == 0` → жива, конец цикла для этой раздачи;
- `failed_counter > 0` и `d.message` содержит транспортную ошибку → `STE_CANT_REACH_TRACKER`, повтор позже;
- `failed_counter > 0` и `d.message` пуст → **кандидат**, идём дальше.

**Защита от массового ложного срабатывания.** Флот выступает собственным контролем:
если доля кандидатов среди раздач одного announce-хоста превышает порог
(предлагается 20%), это отказ трекера, а не волна удалений — весь цикл сворачивается
в `STE_CANT_REACH_TRACKER`. На измеренных данных нормальный уровень — 6 из 246, то есть 2.4%.

**Холодный старт.** После рестарта rTorrent счётчики обнулены. Классификация
пропускается, пока `success_counter + failed_counter == 0`.

### 4.2. Слой 2 — подтверждение анонсом

Только для кандидатов. Анонс на announce-хост из самого торрента, **без passkey**,
с `event=stopped`, `numwant=0`, `compact=1`.

Единственный критерий — **наличие ключа `failure reason`** в bencode-ответе.
Ни интервал, ни число пиров не используются.

Обязательны: последовательное выполнение, пауза между запросами, потолок числа
запросов за цикл, и трактовка `403`/таймаута как «неопределённо», а не как подтверждения.

Слой опционален: при выключении в конфиге кандидаты идут сразу на слой 3.

### 4.3. Слой 3 — классификация по дампу форума

Источник: `https://api.rutracker.cc/v1/static/pvc/f/{forum_id}`, без авторизации.

Требует `forum_id`, которого у плагина нет: в торрент-файле есть только `topic_id`
(в `comment` и `publisher-url`). Эндпоинта `topic_id → forum_id` не существует —
это подтверждено по Swagger-спецификации самого API, а не выведено косвенно.

**Разрешение `forum_id`, три источника по возрастанию цены:**

1. **Кеш.** `forum_id` хранится в custom-поле раздачи (`chk-forum`) после первого разрешения.
2. **Атом-фид.** `feed.rutracker.cc/atom/f/0.atom` даёт `topic_id → forum_id`
   через `<category term="f-NNN">`, а метка `[Обновлено]` в заголовке — независимое
   подтверждение обновления. Окно ~9 часов, покрывает свежие случаи бесплатно.
3. **Разовый обход.** 1261 запрос, ~10–11 минут. Запускается вручную из UI либо
   единожды при первой установке, результат — карта только для своих топиков (~20 КБ).
   Ленивое разрешение «искать форум по мере надобности» отвергнуто: один неизвестный
   топик стоит ~630 запросов, точка безубыточности — две раздачи.

**Классификация по строке дампа:**

| Условие | Статус | Действие |
|---|---|---|
| `info_hash` в дампе ≠ локальный | обновлена | слой 4 |
| `tor_status == 7` | поглощена | новый статус, показать ссылку, **не трогать данные** |
| `tor_status ∈ {1,4,5}` | закрыта / не оформлена / повтор | сообщить, не трогать |
| строки нет | удалена **или перемещена** | см. ниже |
| дамп недоступен | неопределённо | `STE_CANT_REACH_TRACKER` |

**Отсутствие строки нельзя сразу считать удалением.** Топик может быть перемещён
в другой форум — официальный инструмент хранителей это специально обрабатывает
триггером, перезаписывающим `forum_id`. Правило: при отсутствии строки в кешированном
форуме кеш инвалидируется и `forum_id` разрешается заново. Только если топик не
нашёлся и после этого, а трекер независимо подтвердил, что хеш не зарегистрирован —
выставляется `STE_DELETED`. Требуется совпадение двух независимых источников
(трекер и дамп) на протяжении **трёх последовательных циклов**.

### 4.4. Слой 4 — получение нового торрента

Прямое скачивание `.torrent` недоступно: `dl.php` за челленджем, `dl_keeper.php`
требует хранительских ключей. Остаётся добор метаданных по BEP-9.

**Схема — одноразовая служебная закачка** (не подмена на месте):

1. Собрать магнит: `xt=urn:btih:<новый хеш>` + `tr=<announce из старого торрента, с passkey>`.
2. Загрузить его командой `load` (**не** `load.start`) в служебный каталог, затем `d.start`.
   Флаг `start=0` на момент загрузки важен: когда метаданные придут, rTorrent создаст
   реальную раздачу **остановленной**, без несанкционированной записи в каталог данных.
   Старая раздача при этом **не останавливается** и продолжает сидировать.
3. Пометить служебный элемент полями `chk-meta-old`, `chk-meta-topic`, `chk-meta-until` (дедлайн).
4. На следующем цикле: отдельным проходом `d.multicall("main", …)` найти помеченные элементы.
   Метаданные пришли, если элемент перестал быть meta-заглушкой
   (`d.is_meta` на 0.9.7+, иначе `d.name == strtolower(hash) . ".meta"`).
5. Собрать байты `.torrent`, **дописать `comment`** со ссылкой на топик.
   Поле `comment` лежит вне словаря `info`, поэтому хеш не меняется, зато восстанавливается
   сопоставление по regexp комментария и ruTorrent снова показывает ссылку на топик.
6. Отдать байты в **существующий** `createTorrent()` без изменений — со всей нынешней
   транзакцией, точкой коммита, откатом и очисткой осиротевших файлов.
7. По дедлайну: удалить служебный элемент, снять пометки, вернуть раздачу в очередь на повтор.

**Почему не проще.** Прямая подмена магнитом ломает инвариант восстановления после сбоя:
`check.php:380-404` считает, что помеченная подготовленная копия всегда остановлена и закрыта,
а магнит обязан быть запущен, чтобы качать метаданные — эта ветка приняла бы его
за завершённую замену и осиротила. Схема с отдельной закачкой этот инвариант не нарушает.

**Повторное скачивание данных не требуется:** раздача, созданная из метаданных,
не имеет секции быстрого возобновления, поэтому rTorrent автоматически ставит её
на проверку хешей и переиспользует совпавшие куски на диске.

**Планировщик.** `update.php` обходит вид `seeding`; служебная закачка и свежесозданная
замена туда не попадают. Нужен отдельный проход по виду `main` с фильтром по пометкам.

### 4.5. Поглощение

Детект возможен, разрешение — нет. Ни один открытый источник не публикует связь
«старый топик → поглотивший топик»: в дампе нет заголовков, в фиде нет хеша.

Замер распространённости: 11 поглощённых на 226 282 топиков в 13 форумах, то есть
примерно **1 на 20 600**. В восьми форумах из тринадцати их нет вообще.

Решение: новый статус `STE_ABSORBED` с сообщением «раздача поглощена другой, разберитесь
вручную» и ссылкой на топик. Автоматический подбор по схожести заголовка **запрещён** —
сверять не с чем, а ошибка означает перезапись чужой раздачи поверх данных пользователя.

`detectAbsorbedTopic()` и его помощники **сохраняются как есть**. Код живой, покрыт
тестами и оживёт, если челлендж снимут — RuTracker включал и выключал его в марте,
апреле и июле 2026.

## 6. Тестирование

Существующая обвязка `tests/plugins/rutracker_check/` подходит без переделки:
HTTP мокается на уровне класса `Snoopy` картой «URL → ответ», а `NNMClubHandlerTest.php`
уже содержит прецедент мока bencode-ответа трекера.

Фреймворк не вводить — в upstream нет `composer.json`. Запуск:
`docker run --rm -v <worktree>:/app -w /app php:8.1-cli php tests/plugins/rutracker_check/run.php`

Обязательные сценарии:

- `failed_counter > 0` + пустой `d.message` → кандидат;
- `failed_counter > 0` + транспортная ошибка → `STE_CANT_REACH_TRACKER`;
- доля кандидатов выше порога → весь цикл сворачивается;
- `normal_interval = 600` при `failed_counter = 0` → жива (регрессия на отвергнутое правило);
- ответ трекера с `failure reason` и без него;
- дамп: хеш изменился / `tor_status = 7` / строки нет;
- отсутствие строки не даёт `STE_DELETED` с первого раза;
- дедлайн метаданных истёк → откат;
- `comment`, дописанный в метаданные, не меняет `info_hash`.

## 7. Риски

| Риск | Смягчение |
|---|---|
| Расшифровка `tor_status` взята из webTLO, не из документации RuTracker | Статус `7` используется только для сообщения, никогда для действия |
| Статические дампы могут отключить так же, как `get_*` | Слой 1 продолжит работать: он опирается только на BitTorrent-трекер |
| Метаданные могут не прийти (пустой рой на свежей перезаливке) | Дедлайн, откат, старая раздача не останавливалась |
| Перезаливка с изменённой структурой файлов | Проверка хешей вернёт часть кусков, остальное докачается — штатное поведение |
| Лимиты на анонсах (наблюдался `403`) | Слой 2 опционален, только для кандидатов, с паузами и потолком |
| Перемещение топика между форумами | Инвалидация кеша и повторное разрешение перед выводом об удалении |
| Замеры сделаны с одного IP | Поведение Cloudflare может отличаться по стране |

## 8. Вне объёма

- Хранительский путь (`rep.rutracker.cc`, `dl_keeper.php`) — недоступен без статуса хранителя.
- Обход Cloudflare-челленджа в любом виде.
- Автоматическое разрешение поглощений.
- Другие трекеры, кроме RuTracker.
- Восстановление отключённых методов `api.rutracker.cc/v1/get_*`.

- Порог доли кандидатов (предложено 20%) и число циклов подтверждения (предложено 3)
  выбраны из соображений осторожности, а не измерены. Уточнить после наблюдения.
- Служебный каталог для добора метаданных: отдельный подкаталог либо системный временный.
- Нужен ли UI-триггер для разового обхода форумов или достаточно автоматического запуска
  при первой установке.
