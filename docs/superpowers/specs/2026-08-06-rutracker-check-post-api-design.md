# rutracker_check без API RuTracker: дизайн

**Дата:** 2026-08-06
**Статус:** дизайн утверждён; отревьюирован и дополнен вечером 2026-08-06
(пять независимых линз + живые проверки на рабочем экземпляре, включая полную
репетицию слоя 4 и пробу безопасности анонса); реализация не начата
**Предшествующий анализ:** `RUTRACKER-CHECK-ANALYSIS.md` (часть выводов исправлена, см. §3)

---

## 1. Задача

Плагин `plugins/rutracker_check` отслеживает обновление и удаление раздач и подменяет
устаревший торрент новым. Обе опоры, на которых он держался для RuTracker, отвалились:

- `api.rutracker.cc/v1/get_*` отключены (частично с 2026-03-26, полностью с середины июля 2026);
- `rutracker.org/forum/*` закрыт Cloudflare-челленджем (с ~2026-07-27).

Даты зафиксированы по наблюдениям с рабочего экземпляра и Wayback; официальные
объявления недоступны (сам форум за челленджем).

Требуется вернуть работоспособность, не обходя защиту: только те источники, которые
RuTracker отдаёт открыто, плюс сам протокол BitTorrent.

**Охват:** только хендлер RuTracker. `nnmclub.php`, `toloka.php` и прочие не трогаем.

**Решения, зафиксированные с пользователем:**

- аккаунт обычный, не хранительский — хранительский путь (`rep.rutracker.cc`, `dl_keeper.php`) недоступен;
- подмена раздачи должна быть автоматической;
- строим полный автомат сразу, а не поэтапно;
- слой 2 включён по умолчанию (решение после пробы безопасности, §2.8);
- разовый обход форумов запускается автоматически, без UI-триггера (§4.3);
- реализация ведётся в отдельном worktree.

**Инвариант:** новый поток не делает ни одного запроса к `rutracker.org`.

## 2. Что проверено на живой системе

Всё ниже измерено 2026-08-06 на рабочем экземпляре пользователя, а не выведено из
документации. §2.1–2.6 — дневная сессия; §2.7–2.9 — вечерняя (в рамках ревью).

**Окружение:** rTorrent 0.16.19, libtorrent 0.16.19, XMLRPC API 24, 397 раздач,
из них 246 с трекером `*.t-ru.org` (по announce-хостам: bt — 57, bt2 — 66, bt3 — 57, bt4 — 66).

### 2.1. Детектор: `t.failed_counter` работает, `d.message` — вспомогателен

Раздачи разбиты на три группы, каждая проверена независимым запросом к трекеру
(анонс без passkey, `event=stopped`):

| Группа | Локальный признак | Вердикт трекера |
| --- | --- | --- |
| 6 раздач | `t.failed_counter > 0` | не зарегистрированы — **6 из 6** |
| 10 раздач | `t.normal_interval = 600` | зарегистрированы — **10 из 10** |
| 8 раздач | здоровые | зарегистрированы — **8 из 8** |

Разделение без пересечений: ни одного ложного срабатывания на 18 контрольных.

`d.message` пуст у всех 246 раздач, включая шесть мёртвых. По всем 397 раздачам он
непустой лишь у пяти, и только с транспортными ошибками
(`Tracker: [Could not resolve hostname]`, `[Could not connect to server]`).

**Уточнение механизма (по исходникам 0.16.19, ревью).** Текст `failure reason`
*доходит* до `d.message` (цепочка `tracker_http.cc receive_failed → tracker_list.cc
→ download_wrapper.cc → m_message`), но поле хранит только последнее трекер-событие
любой строки раздачи: успешный анонс любой другой строки (retracker и т.п.) стирает
его. Поэтому эмпирически поле пусто и полагаться на него нельзя. Вывод прежний:
первичный сигнал — `t.failed_counter`, а `d.message` — лишь вспомогательный
дискриминатор «трекер недоступен» против «раздача снята», причём только когда его
текст относится к хосту RuTracker.

### 2.2. Интервал анонса не является признаком

`normal_interval = 600` (нижняя граница клампа libtorrent) встретился у 29 раздач —
все они живы. Правило из исходного анализа («короткий интервал = мертва») дало бы
29 ложных удалений из 246. Правило отвергнуто.

### 2.3. Магнит-путь применим

`d.is_private = 0` у **всех 246** раздач RuTracker. DHT, PEX и добор метаданных
по BEP-9 разрешены. BEP-9 требует пиров, а не DHT — HTTP-трекер их отдаёт.
DHT на живом экземпляре активен (`dht.statistics: active=1, nodes=163`).

### 2.4. Цепочка «мёртвый хеш → новый хеш» проходит целиком

Два случая доведены до конца на реальных данных:

- топик 6880555: найден в `feed.rutracker.cc/atom/f/0.atom` с меткой `[Обновлено]`,
  оттуда получен `forum_id = 1106`, из дампа форума — новый `info_hash`, отличный от локального;
- топик 6868321: найден обходом дампов в форуме 921 («Мультсериалы»),
  `tor_status = 0`, 45 сидов, новый `info_hash`.

Вечером того же дня все шесть мёртвых топиков разрешились через два дампа
(пять — форум 1106, один — форум 921), у всех новый хеш, `tor_status = 0`, живые сиды.

### 2.5. Стоимость обхода дампов подтверждена

140 форумов за 70 секунд при **6 параллельных** соединениях, 50.4 МБ после распаковки.
Экстраполяция на все 1261 форумов: **около 10–11 минут при той же параллельности**;
последовательно — порядка часа. Ограничение параллельности учтено в §4.3.

`feed.rutracker.cc/atom/f/0.atom` отдаёт ровно 300 записей глубиной ~9 часов,
из них 86 с меткой `[Обновлено]`. Пять из шести мёртвых топиков в это окно не попали —
фид годится как ускоритель, но не как основной источник.

### 2.6. Активные анонсы лимитируются

После примерно сорока анонсов трекер начал отвечать `403`. Это прямое подтверждение,
что активный опрос не может быть основным механизмом и должен применяться только
к кандидатам, отобранным бесплатным локальным детектором.

### 2.7. Репетиция слоя 4 на живом клиенте

Полный цикл добора метаданных проверен на реальном обновлении (топик 6879823,
новый хеш из дампа форума 1106, 73 сида):

- магнит загружен командой `load` (не `load.start`) с custom-полем и каталогом,
  переданными **параметрами самой команды load**;
- заглушка появилась в виде `main` (в `seeding` не попала), остановленной:
  `d.is_meta = 1`, `d.name = <ХЕШ_ВЕРХНИМ_РЕГИСТРОМ>.meta` — регистр **верхний**;
- после `d.start` метаданные пришли **за 4 секунды**;
- реальная раздача создана **остановленной и закрытой** (`state=0, is_open=0,
  is_active=0`) — флаг `start=0` исходного `load` пережил превращение;
- custom-поле, переданное параметром load, **пережило** превращение заглушки
  в реальную раздачу;
- уборка чистая: после `d.erase` служебного элемента парк вернулся в исходное
  состояние, старая раздача не пострадала.

### 2.8. Проба безопасности анонса: `stopped` не выбивает живой пир

Худший сценарий слоя 2 проверен на раздаче с минимальным роем (`bt.t-ru.org`):
с того же IP, что и клиент пользователя, отправлен анонс `event=stopped, left=0,
numwant=0` **без passkey**, с чужим peer_id и портом. Реальный пир пользователя
(`IP:45000`) остался в списке пиров трекера до и после — трекер ключует пиров
не по IP, а по peer_id/порту. При **отличающейся** идентичности пробы слой 2
безопасен; совпадающая идентичность сознательно не проверялась и запрещена (§4.2).

Дополнительно: ответ `/ann` у t-ru **не содержит** ключей `complete`/`incomplete` —
никакие счётчики из ответа использовать нельзя.

### 2.9. Прочие живые факты

- Статика `api.rutracker.cc` отвечает `403` на User-Agent `Python-urllib`;
  дефолтный UA Snoopy и `curl/*` проходят. UA обязан задаваться явно, `403`
  трактуется как «дамп недоступен».
- В `comment`/`publisher-url` торрент-файлов — только `viewtopic.php?t=<topic_id>`:
  проверено на 14 случайных раздачах 2008–2026 годов. `forum_id` в файлах нет
  ни в каком поле; XMLRPC-доступа к `comment` у rTorrent нет вовсе.
- В rTorrent 0.16 действует разделение trusted/untrusted XMLRPC-соединений.
  Серверный PHP форка помечает свои запросы как trusted (`UNTRUSTED_CONNECTION`
  в `php/xmlrpc.php`), поэтому для плагина ограничений нет; новый код тем не менее
  не должен полагаться на команды-перечисления (`d.custom.keys`, `d.custom.items`).

`0` не проверено, `1` закрыто, `2` проверено, `3` недооформлено, `4` не оформлено,

## 4. Архитектура

Четыре слоя. Каждый следующий дороже предыдущего и вызывается только для того,
что предыдущий не смог закрыть.

```text
Слой 1  локальный детект (0 запросов)      → отсеивает ~97% раздач
   ↓ кандидаты
Слой 2  подтверждение анонсом (опционально) → снимает холодный старт
   ↓ подтверждённые
Слой 3  классификация по дампу форума       → обновлена / удалена / поглощена
   ↓ обновлённые
Слой 4  добор метаданных магнитом           → байты .torrent → существующая транзакция
```

### 4.1. Слой 1 — локальный детект

Расширяем существующий `t.multicall` в `update.php:18` полями
`t.failed_counter`, `t.success_counter`, `t.activity_time_last`, `t.is_enabled`
и добавляем `d.message` в `d.multicall`. Формат встраивания зафиксировать при
реализации явно (разделитель полей внутри вложенного `t.multicall`, новый шаг
чтения в цикле разбора) — значения URL не должны ломать разбор.

Счётчики берутся **только со строки трекера, чей `t.url` соответствует хендлеру**
(`t-ru.org`); прочие строки (dht://, retracker) игнорируются. Строки с
`t.is_enabled = 0` пропускаются; `t.activity_time_last` — санитарная проверка,
что анонс вообще выполнялся.

Правило (для каждой раздачи независимо):

- `failed_counter == 0` → жива, конец цикла для этой раздачи;
- `failed_counter > 0` и `d.message` содержит транспортную ошибку **с упоминанием
  хоста RuTracker** → `STE_CANT_REACH_TRACKER`, повтор позже;
- `failed_counter > 0`, `d.message` пуст или относится к другому трекеру → **кандидат**,
  идём дальше. `d.message` — только вспомогательный сигнал (§2.1): он мог быть
  затёрт успехом другой строки.

**Защита от массового ложного срабатывания.** Флот выступает собственным контролем.
Предохранитель срабатывает **по announce-хосту** и только когда
`кандидатов ≥ max(3, ceil(0.2 × размер группы))`. Живые группы — 57–66 раздач на
хост (§2), то есть порог ≈ 12–14. При срабатывании в `STE_CANT_REACH_TRACKER`
уходят **только кандидаты этого хоста**; здоровые раздачи сохраняют свои статусы.
Группы меньше абсолютного пола (3) предохранитель пропускают — их страхуют слои 2–3
с многоцикловым подтверждением. Нормальный уровень на измеренных данных —
6 из 246 (2.4%).

**Холодный старт.** Счётчики обнуляются рестартом rTorrent **и любым
`d.stop`/`d.start`** (включая откат `createTorrent()`) — это штатно и лишь
задерживает детект на один анонс. Пока `success_counter + failed_counter == 0`
на строке RuTracker, классификация **этой раздачи** пропускается (скоуп —
раздача, не цикл).

### 4.2. Слой 2 — подтверждение анонсом

Только для кандидатов. Анонс на announce-хост из самого торрента, **без passkey**,
с `event=stopped`, `numwant=0`, `compact=1`.

**Идентичность пробы (обязательно).** Полный набор параметров (без них `/ann`
отвечает 403): `info_hash` (20 бинарных байт, urlencoded), `peer_id` — 20 байт
с фиксированным префиксом плагина (например `-RC0001-` + 12 случайных байт),
заведомо отличным от peer_id rTorrent; `port` — фиксированный высокий порт **вне
`network.port_range` клиента**; случайный `key`; `uploaded=0&downloaded=0&left=0`.
Отличные от rTorrent peer_id, порт и key обязательны: `event=stopped` удаляет
запись пира у трекера, а трекеры идентифицируют пиров по peer_id, (ip, port)
или (ip, key). С отличающейся идентичностью безопасность проверена живьём (§2.8).

**Критерий вердикта.** «Не зарегистрирована» — только когда тело ответа
декодируется в bencode-**словарь**, содержащий ключ `failure reason` с текстом,
совпадающим с зафиксированным текстом трекера для незарегистрированного хеша
(точный текст записать при реализации по первому замеру). «Зарегистрирована» —
HTTP 200, bencode-словарь, ключа `failure reason` нет. Всё прочее — не-bencode,
пустое тело, HTML, обрыв, 403, таймаут — «неопределённо», не подтверждение.
Счётчики `complete`/`incomplete` в ответе t-ru отсутствуют (§2.8) и не используются;
интервал и пиры — тоже.

**Лимиты.** Последовательное выполнение; пауза 5–10 с со случайным джиттером;
потолок **10 анонсов за цикл на announce-хост** (наблюдаемый лимит ~40, §2.6, запас 4×).
Первый же `403` прекращает слой 2 для хоста до конца цикла и записывает
**персистентный кулдаун** (пропустить хост N следующих циклов; N удваивается до
суточного максимума, сбрасывается успешным анонсом). Потолок действует и для
ручных проверок (`batch_check.php`).

Слой опционален, **по умолчанию включён**. При выключении кандидаты идут сразу
на слой 3, но условие двух независимых источников для `STE_DELETED` (§4.3)
становится невыполнимым: в этом режиме `STE_DELETED` не выставляется никогда,
отсутствующие в дампе топики остаются в `STE_CANT_REACH_TRACKER` с пояснением
в `chk-msg`.

### 4.3. Слой 3 — классификация по дампу форума

Источник: `https://api.rutracker.cc/v1/static/pvc/f/{forum_id}`, без авторизации,
но **с обязательным явным User-Agent** (§2.9; `403` на «голые» UA = «дамп недоступен»).

Требует `forum_id`, которого у плагина нет: в торрент-файле есть только `topic_id`
(в `comment` и `publisher-url`; проверено на 14 раздачах 2008–2026, §2.9).
Эндпоинта `topic_id → forum_id` не существует — это подтверждено по
Swagger-спецификации самого API, а не выведено косвенно.

**Разрешение `forum_id`, три источника по возрастанию цены:**

1. **Кеш.** `forum_id` хранится в custom-поле раздачи (`chk-forum`) после первого
   разрешения (session-persistent, отдельный файл карты не нужен).
2. **Атом-фид.** `feed.rutracker.cc/atom/f/0.atom` даёт `topic_id → forum_id`
   через `<category term="f-NNN">`, а метка `[Обновлено]` в заголовке — независимое
   подтверждение обновления. Окно ~9 часов. **`update.php` скачивает фид раз в цикл**
   условным GET; выученные пары для своих топиков сразу пишутся в `chk-forum`,
   отметка `[Обновлено]` по своему топику — в `chk-feed-upd` (метка времени).
3. **Полный обход.** 1261 запрос. Запускается **автоматически**: единожды при
   первой установке и далее при появлении неразрешённых топиков, но не чаще
   кулдауна (по умолчанию 24 ч). UI-триггер не строится. Выполняется фоновым
   процессом (по образцу `batch_check`), не внутри цикла `update.php`:
   при 6 параллельных соединениях ~10–11 минут (§2.5), последовательно ~час —
   механизм параллельности решается в плане реализации, потолок — 6 соединений.
   Результат — карта только для своих топиков (~20 КБ) → в `chk-forum`.
   Ленивое разрешение «искать форум по мере надобности» отвергнуто: один
   неизвестный топик стоит ~630 запросов, точка безубыточности — две раздачи.

**Очередь обхода.** Неразрешённые `topic_id` (промах кеша, инвалидация,
свежедобавленные раздачи, не попавшие в окно фида) копятся в очереди; один обход
за запуск разрешает **всю очередь**. Топик, не найденный и обходом, помечается
(`chk-forum-miss` с меткой времени) и не запускает новые обходы до кулдауна.
Очередь, ETag'и дампов и метки кулдауна живут в файле в каталоге настроек плагина.

**Экономия трафика.** Для каждого форума хранится ETag/Last-Modified; запросы идут
с `If-None-Match`/`If-Modified-Since` (`304` → использовать кешированный разбор);
gzip обязателен. В пределах цикла дамп форума скачивается не более одного раза,
сколько бы кандидатов на него ни пришлось.

**Классификация по строке дампа — порядок правил строгий:**

| # | Условие | Статус | Действие |
| --- | --- | --- | --- |
| 1 | строки нет | удалена **или перемещена** | см. ниже |
| 2 | `tor_status == 7` | поглощена | `STE_ABSORBED`, показать ссылку, **не трогать данные** |
| 3 | `tor_status ∈ {1, 4, 5}` | закрыта / не оформлена / повтор | сообщить, не трогать |
| 4 | `tor_status ∈ {6, 9, 11}` или неизвестный | неопределённо | повторить в следующем цикле |
| 5 | `tor_status ∈ {0, 2, 3, 8, 10}` и `info_hash` ≠ локальный | обновлена | слой 4 |
| 6 | `tor_status ∈ {0, 2, 3, 8, 10}` и `info_hash` совпал | жива | `STE_UPTODATE` |
| — | дамп недоступен (в т.ч. 403 по UA) | неопределённо | `STE_CANT_REACH_TRACKER` |

Сравнение хеша выполняется **только** при валидном `tor_status` — слой 4 никогда
не запускается по строке со статусом вне `{0, 2, 3, 8, 10}`.

**Отсутствие строки нельзя сразу считать удалением.** Топик может быть перемещён
в другой форум — официальный инструмент хранителей это специально обрабатывает
триггером, перезаписывающим `forum_id`. Правило: при отсутствии строки в кешированном
форуме кеш инвалидируется и топик ставится в очередь переразрешения (фид → обход
по кулдауну). Только если топик не нашёлся и после этого, а трекер независимо
подтвердил, что хеш не зарегистрирован — выставляется `STE_DELETED`. Требуется
совпадение двух независимых источников (трекер и дамп) на протяжении
**трёх последовательных циклов**.

**Счётчик подтверждения** хранится на раздаче: `chk-del` в формате
`счёт:метка_времени_последнего_инкремента`. Инкремент — не чаще одного раза
в `updateInterval`, независимо от способа запуска (ручная проверка переиспользует
метку — накрутить три цикла за минуту нельзя). Сбрасывается в ноль, когда: строка
топика снова появилась в дампе, либо анонс прошёл успешно (хеш зарегистрирован),
либо `failed_counter` вернулся в 0.

`STE_DELETED` — **только индикация** (иконка + `chk-msg`), как и сегодня;
автоматическая остановка или удаление данных по этому статусу запрещены.
Остаточный риск ложного срабатывания — неверная пометка в UI, не потеря данных.

### 4.4. Слой 4 — получение нового торрента

Прямое скачивание `.torrent` недоступно: `dl.php` за челленджем, `dl_keeper.php`
требует хранительских ключей. Остаётся добор метаданных по BEP-9.

**Схема — одноразовая служебная закачка** (не подмена на месте). Репетиция полного
цикла на живом клиенте — §2.7.

0. **Предусловие.** Проверить, не существует ли новый хеш уже в клиенте
   (пользователь заменил вручную): `load` глотает дубликаты **молча**, поэтому
   проверка обязательна до загрузки. Если существует — магнит не грузить,
   маркеры не ставить, выставить `chk-msg` «новый торрент уже загружен вручную»
   и `STE_NOT_NEED`.

1. **Магнит:** `xt=urn:btih:<новый хеш>` + `tr=<announce из старого торрента, с passkey>`.

2. **Загрузка.** Командой `load` (**не** `load.start`) — и все пометки передаются
   **параметрами самой команды load** (`$addition` в `sendMagnet()` это уже умеет):
   служебный каталог (`d.directory.set=` подкаталог под `$topDirectory`, например
   `.chk-meta` — системный temp не пройдёт `correctDirectory`) и маркеры
   `chk-meta-old=<старый хеш>`, `chk-meta-topic=<topic_id>`,
   `chk-meta-until=<unix-время дедлайна>`.

   **Почему именно параметрами load.** Когда метаданные приходят, rTorrent
   *стирает* заглушку и создаёт реальную раздачу заново, перенося только параметры
   исходной команды `load` (`commands`, `start`, `print_log` из
   `rtorrent_meta_download`; `download_factory.cc`, `manager.cc
   try_create_download_from_meta_download`). Custom-поля, выставленные отдельным
   `d.custom.set` **после** загрузки, при превращении теряются. Тот же механизм
   сохраняет `start=0`: реальная раздача создаётся **остановленной**, без
   несанкционированной записи в каталог данных (проверено живьём, §2.7).
   Старая раздача при этом **не останавливается** и продолжает сидировать.

   Одновременно **авторитетное состояние пишется на старую раздачу** (обычная,
   session-persistent, переживает и рестарт, и превращение заглушки):
   `chk-state = STE_META_PENDING`, `chk-meta-new=<новый хеш>`,
   `chk-meta-until=<дедлайн>`. Заглушка несёт зеркальные метки.

3. **Синхронизация.** `load` асинхронен: дождаться появления хеша в клиенте
   (паттерн `waitForLoad()` из `check.php`); таймаут → цикл неуспешен, маркеры
   снять, старая раздача нетронута. Затем `d.start` заглушки — без старта
   метаданные не качаются.

4. **Ожидание (следующие циклы).** Пока `chk-state == STE_META_PENDING` и элемент
   для `chk-meta-new` существует, `run()` **не классифицирует раздачу заново и не
   шлёт магнит повторно**. Отдельный проход обходит старые раздачи с
   `STE_META_PENDING` и находит служебный элемент **адресно по хешу** из
   `chk-meta-new` (не сканированием пометок). Метаданные пришли, если
   `d.is_meta == 0` (0.16.19; фолбэк для старых rTorrent:
   `d.name == strtoupper(hash) . ".meta"` — регистр **верхний**, §2.7).
   Досрочный отказ: `t.failed_counter > 0` у служебного элемента — трекер не
   признал новый хеш; элемент удалить, кандидата вернуть на слой 3, дедлайна
   не ждать. Сироты (элементы с `chk-meta-old`, чья старая раздача потеряла
   `STE_META_PENDING`) удаляются по своему `chk-meta-until`.

5. **Сбор байтов — строго в этом порядке:**

   а) прочитать байты session-файла через `rTorrent::getSource(<новый хеш>)`
      — **до** удаления элемента: `d.erase` стирает `session/<hash>.torrent`,
      после него байты взять неоткуда;

   б) валидировать: `new Torrent(...)` без ошибок и `hash_info()` равен ожидаемому
      новому хешу; провал → удалить элемент, вернуть кандидата в очередь на повтор.
      Отдавать непроверенные байты в `createTorrent()` нельзя: его legacy-контракт
      превращает нечитаемый вход в `STE_DELETED`;

   в) проверить `announce` (rTorrent сохраняет `tr=` из магнита; при отсутствии —
      вписать announce старого торрента с passkey) и **дописать `comment`** со
      ссылкой на топик. Оба поля вне словаря `info` — хеш не меняется, зато
      восстанавливается сопоставление по regexp комментария и ruTorrent снова
      показывает ссылку на топик;

   г) удалить служебный элемент (`d.erase`) и убедиться, что
      `torrentExists(<новый хеш>) === false`. Без этого `createTorrent()` найдёт
      хеш уже загруженным и, поскольку элемент несёт `chk-meta-*`, а не
      `chk-replacement`, вернёт `STE_ERROR` («чужой элемент», `check.php:378-393`)
      — **на каждой подмене**. Помечать служебный элемент `chk-replacement` нельзя:
      нарушится инвариант «помеченная копия всегда остановлена и закрыта»
      (см. «Почему не проще»);

   д) только теперь отдать байты в **существующий** `createTorrent()` — он
      действительно остаётся без изменений: со всей нынешней транзакцией, точкой
      коммита, откатом и очисткой осиротевших файлов.

   Окно сбоя между (г) и (д) безопасно: старая раздача сохраняет
   `STE_META_PENDING` и `chk-meta-new`; следующий цикл не найдёт элемента по хешу
   и просто начнёт добор заново. Ничего не осиротевает.

6. **Дедлайн** (`chk-meta-until`, wall-clock, по умолчанию 24 ч; в репетиции
   метаданные пришли за 4 секунды — запас велик): удалить служебный элемент,
   снять маркеры и `STE_META_PENDING`, вернуть раздачу в очередь на повтор.

**Почему не проще.** Прямая подмена магнитом ломает инвариант восстановления после сбоя:
`check.php:380-404` считает, что помеченная подготовленная копия всегда остановлена и закрыта,
а магнит обязан быть запущен, чтобы качать метаданные — эта ветка приняла бы его
за завершённую замену и осиротила. Схема с отдельной закачкой этот инвариант не нарушает —
именно поэтому служебный элемент удаляется **до** вызова `createTorrent()`, а не
маркируется его маркером.

**Повторное скачивание данных не требуется:** раздача, созданная из метаданных,
не имеет секции быстрого возобновления, поэтому rTorrent автоматически ставит её
на проверку хешей и переиспользует совпавшие куски на диске. Перезаливка с изменённой
структурой файлов — штатный случай: совпавшие куски вернутся, остальное докачается.

**Планировщик.** `update.php` обходит вид `seeding`; служебная закачка и свежесозданная
замена туда не попадают (проверено, §2.7). Нужен отдельный проход: старые раздачи
с `STE_META_PENDING` → адресный поиск служебных элементов по `chk-meta-new`
(в виде `main`), плюс подбор сирот.

### 4.5. Поглощение

Детект возможен, разрешение — нет. Ни один открытый источник не публикует связь
«старый топик → поглотивший топик»: в дампе нет заголовков, в фиде нет хеша.

Замер распространённости: 11 поглощённых на 226 282 топиков в 13 форумах, то есть
примерно **1 на 20 600**. В восьми форумах из тринадцати их нет вообще.

Решение: новый статус `STE_ABSORBED` с сообщением «раздача поглощена другой, разберитесь
вручную» и ссылкой на топик. Автоматический подбор по схожести заголовка **запрещён** —
сверять не с чем, а ошибка означает перезапись чужой раздачи поверх данных пользователя.

`detectAbsorbedTopic()` и его помощники **сохраняются как есть**, но из активного
пути исключаются (вместе с обращением к `dl.php`): функции спят и оживут, если
челлендж снимут — RuTracker включал и выключал его в марте, апреле и июле 2026.

### 4.6. Диагностика

Каждый слой логирует свой вердикт по кандидату через существующий `logDebug`:
слой 1 — значения счётчиков и `d.message`; слой 2 — исход анонса; слой 3 — строка
дампа и `tor_status`; слой 4 — прогресс добора. `chk-msg` несёт человекочитаемую
причину текущего статуса (например «дамп: строки нет, цикл 2/3») и показывается
в существующей строке результата в UI.

## 6. Тестирование

Существующая обвязка `tests/plugins/rutracker_check/` подходит: HTTP мокается
на уровне класса `Snoopy` картой «URL → ответ» (`NNMClubHandlerTest.php` содержит
прецедент мока bencode-ответа трекера), **XMLRPC-сценарии — дублем
`rXMLRPCRequest`**. Для этого логика слоёв обязана жить в методах классов,
а не в теле `update.php` (см. §5).

Фреймворк не вводить — в upstream нет `composer.json`. Запуск:
`docker run --rm -v <worktree>:/app -w /app php:8.1-cli php tests/plugins/rutracker_check/run.php`

Обязательные сценарии:

- `failed_counter > 0` + пустой `d.message` → кандидат;
- `failed_counter > 0` + транспортная ошибка RuTracker-хоста → `STE_CANT_REACH_TRACKER`;
- предохранитель: кандидаты ≥ max(3, 20% группы) → сворачиваются только кандидаты хоста;
- ниже пола (1–2 кандидата в малой группе) → предохранитель молчит;
- `normal_interval = 600` при `failed_counter = 0` → жива (регрессия на отвергнутое правило);
- ответ трекера: словарь с `failure reason` / словарь без него / не-bencode / пустое тело → «неопределённо»;
- дамп: хеш изменился при валидном `tor_status` / `tor_status = 7` / `tor_status = 9` (не действие) / строки нет;
- отсутствие строки не даёт `STE_DELETED` с первого раза; `chk-del` не инкрементируется чаще `updateInterval`; сброс `chk-del` по возврату строки;
- слой 2 выключен → `STE_DELETED` недостижим;
- предусловие слоя 4: новый хеш уже существует → магнит не грузится;
- маркеры передаются параметрами load (проверка собранной команды);
- имя заглушки сравнивается в **верхнем** регистре;
- валидация байтов: хеш не совпал → повтор, не `STE_DELETED`;
- порядок 5а–5д: попытка `createTorrent()` при существующем служебном элементе → ошибка (регрессия);
- рестарт с зависшим `STE_META_PENDING` (элемент есть / элемента нет / сирота);
- дедлайн метаданных истёк → откат;
- `comment`, дописанный в метаданные, не меняет `info_hash`.
