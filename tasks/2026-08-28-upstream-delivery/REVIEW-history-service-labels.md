# Перепроверка `up/history-service-labels`

Дата: 2026-08-28. Проверенная вершина после переноса на актуальный
`upstream/master` (`fde9863b`) — `4cf3bd69`.

## Вердикт

**В таком виде не отправлять.** Ветка вносит достижимую потерю пользовательской
истории и Pushbullet-уведомлений, а её тест не проверяет production-gate.

Само наблюдение, ради которого ветка была сделана, реально: служебный BEP-9 stub
из форкового `rutracker_check` после получения metadata принимает имя настоящего
торрента, и его удаление нельзя отличить по имени. Ошибка находится в выбранном
идентификаторе: произвольная пользовательская метка с ведущей точкой объявлена
служебной.

## Подтверждённый контрпример

1. UI разрешает создать метку `.private`: `js/webui.js::createLabel()` только
   обрезает пробелы и заменяет кавычки.
2. `setlabel` передаёт её в `d.custom1` без запрета ведущей точки.
3. Обработчики addition/finish/deletion каждый раз читают `d.get_custom1`.
4. `update.php` вызывает `isServiceEntry()`, где любая строка, начинающаяся с
   `.`, возвращает `true`.
5. Один и тот же guard пропускает и `$hst->add()`, и `pushBulletNotify()`.

Следовательно, обычный торрент с меткой `.private` теряет все три события и все
настроенные уведомления. Если поставить метку после добавления, исчезают только
последующие finish/deletion. В multi-user установке `d.custom1` общий, поэтому
события исчезают из истории каждого пользователя с зарегистрированным handler.

Контрпример был добавлен во временную рабочую копию:

```text
not ok - a dot-labelled service download is not the user's event either
RuntimeException: a user label that deliberately starts with a dot must be kept;
expected false, got true
7 tests, 1 failures
```

После измерения временная правка удалена; рабочее дерево ветки чистое.

## Вторая проблема: тест не держит место применения

`HistoryDataTest.php` вызывает только чистый `isServiceEntry()`. В отдельной
копии `update.php` был возвращён к старому `isMagnetPlaceholder()`; тест после
этой мутации всё равно дал `7 tests, 0 failures`. Значит, suite не замечает
регрессию, при которой новый классификатор вообще не применяется перед записью
истории и уведомлением.

## Ветка не исправляет текущий upstream call graph

В `upstream/master` нет producer-а `.chk-meta` и нет metadata-fetcher-а, который
создаёт такой download. Строка встречается только в новом комментарии и тесте.
Настоящий producer пока существует только в форковом
`plugins/rutracker_check/metafetch.php`; вместе с точной меткой он несёт более
сильный marker `chk-meta-old`.

Таким образом standalone-PR сейчас добавляет глобальную семантику пользовательских
меток, но не исправляет ни одного существующего upstream-пути.

## Что делать вместо отправки

Логику следует перенести в PR с самим metadata-fetcher-ом. Идентичность stub-а
нужно строить по принадлежащему plugin-у marker-у `chk-meta-old`, а не по
пространству пользовательских меток. Перед реализацией необходимо в `rt-lab`
измерить, что marker уже виден во всех трёх rTorrent events, включая insertion.
Regression test должен запускать настоящий путь `history/update.php` и отдельно
доказывать обе стороны:

- service marker не создаёт строку истории и уведомление;
- обычные метки `.private`, `.chk-meta/archive` и `Video/4K.HDR` остаются
  пользовательскими.

Сужение только до точной метки `.chk-meta` убирает массовую регрессию, но не
устраняет зависимость от изменяемого пользователем label и коллизию с обычной
меткой, поэтому как окончательная правка не принято.
