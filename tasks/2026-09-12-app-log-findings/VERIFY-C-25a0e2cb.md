## Уточнения к ARCHITECTURE

1. R1 разумно убирает второго писателя UPTODATE для foreign-строк, но не снимает недоказанную посылку «живой announce означает живую тему». Он лишь ограничивает потенциально пропущенное обновление периодом rest, **если** due-строка реально получит dispatch. При cap это условие требует отдельного контроля.
2. **Критерий `chk-time` у Kinozal/NNMClub/Toloka «движется каждый цикл» противоречит самому R1.** R1 пропускает свежий UPTODATE до ~24 часов; существующий `isSettled()` оставляет `NOT_NEED+superseded` на неделю. Не надо стимулировать запись `chk-time` без ответа только ради графика. Проверять age p50/p95/max по состояниям и отношение `eligible / dispatched / postponed / capped`, отдельно для каждого handler.
3. **Cap «на обработчик» нельзя вывести из нынешнего `ownerOf()`.** Точный `topicPattern` объявлен только у Kinozal (`kinozal.php:456–460`); RuTracker, NNMClub, Toloka, tfile, AniDUB, TapochekNet его не объявляют. `ownerOf()` для них отвечает null. До cap нужны точные объявления/проверка соответствия handler decline, либо явный безопасный fallback; использовать первый loose comment filter снова даст прежнюю ошибку владения.
4. **Сортировка cap только по старому `chk-time` может голодать.** Удержанный terminal+retryable намеренно не обновляет `chk-time` (`check.php:2163–2170`). При cap одни и те же старые неуспешные строки первыми займут квоту каждый цикл, а другие due-строки могут никогда не попасть в handler. Нужен отдельный `last_attempt`, rotating cursor или доказанный механизм справедливости; сохранять `chk-time` как время последнего ответа.
5. Тестовое обещание «ни одного `d.set_custom` для чужой строки» нужно ограничить **веткой пропуска**, поскольку настоящая `dispatchChecker()` вызывает checker, который пишет state/time. Для капа тестировать отсутствие записи у skipped/postponed и отсутствие необоснованного UPTODATE, а также прогресс due-строк через несколько циклов.
6. Решение «Kinozal не трогать две недели» должно явно учитывать известные C4/C5 и вести счёт `details 403 → download outcome`, `cycleAbandoned`, `downloadAbandoned`, возраст неотвеченных тем. Пробу на конкретную перезалитую/удалённую тему проводить только чтением; возраст `chk-time` сам по себе не доказывает, что новая версия найдена.
7. Цифры 18–22 дня и «первые два ревью дадут 30–45 пунктов» являются оценками/экстраполяцией панели, а не измеренным свойством кода. В плане их следует маркировать как оценку.

## Дополнительные находки вне C1–C41

**VC-NEW-2 (P2, подтверждённый реальный ответ, старый код): Tapochek считает удалённую тему недоступной.** 2026-09-25 читающий GET `https://tapochek.net/viewtopic.php?p=7` ответил HTTP 200, `text/html; charset=windows-1251`, 11 391 байт. Точные сырые байты сохранены в [`verify-c-evidence/tapochek-p7-2026-09-25.html`](verify-c-evidence/tapochek-p7-2026-09-25.html), SHA-256 `541b85acf6a7aed472a2a7b070f8806bdd4708a6777fd98c3f46cdba426997ba`. Запрос был анонимным `curl`, без cookies и учётных данных; два hidden-поля `form_token`/`sid` в ответе пусты. В теле есть `<table class="forumline message">`, заголовок «Информация» и точная cp1251-фраза «Темы, которую вы запросили, не существует.»; `btih:` и download href отсутствуют.

На **полном живом теле** `TapochekNetCheckImpl::isMissingAnswer()` отвечает false; на одной извлечённой внутренней таблице — true. Под PHP85 из поставляемого образа без iconv (сеть выключена) получили `iconv=no full=CANT_REACH isolated=DELETED bytes=11391`. Причина на [`tapocheknet.php:35`](../../plugins/rutracker_check/trackers/tapocheknet.php#L35): `preg_match_all('<table...>.*?</table>')` начинает блок с более ранней внешней `<table class="table-full-width">` и заканчивает его первым `</table>` внутренней `forumline message`. Из шести найденных regex-таблиц ни одна не имеет class `forumline`; настоящий deletion marker проглочен внешним блоком. Поскольку status=200 и нет `btih`, handler после ложного `isMissingAnswer()` возвращает STE_CANT_REACH_TRACKER вместо STE_DELETED (`tapocheknet.php:61–92`). Это неправильный вердикт на реально наблюдённом входе, хотя затронутых Tapochek-торрентов на проде здесь не доказано. По принятой шкале «узкий реалистичный вход» — P2. Дополнительная независимая проверка **полного** `download_torrent()` с этой fixture через `TestLib` wire-double дала `result=5`, `STE_CANT_REACH_TRACKER=5`, `STE_DELETED=4` (`php -n`, без обращения к rTorrent). Поэтому ошибка не ограничена приватным helper. Строка `tests24` в CHECK правильно отмечает исправление CP1251-байт, но её широкое обещание «удалённая тема теперь даёт STE_DELETED в прод-образе» опровергается этой реальной страницей.

**VC-NEW-1 (nit, старый код):** AniDUB, tfile, Toloka и Tapochek повторно используют `Snoopy` после topic-page, вызывают `fetchComplex(download)` без проверки bool (`trackers/anidub.php:68–71`, `tfile.php:19–21`, `toloka.php:57–61`, `tapocheknet.php:76–78`). Исправление при очередном проходе по этим handler: проверять bool и классифицировать отказ до чтения `status/results`; не менять verdict без снятого реального ответа.
