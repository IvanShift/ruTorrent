## Исправления и новые находки в плане

### A1. Не указан перенос четырёх поздних коммитов после выпуска шага 0

`git merge-base 74aea456 master` даёт `74aea456`, а `git rev-list --count 74aea456..master` даёт 4. Поэтому ветка от `74aea456` с тестовой правкой **может** fast-forward опубликованный `origin/master=1fa8defc`, но **не может** fast-forward текущий локальный `master=25a0e2cb`. Фраза шага 0 «fast-forward master» ([архитектура:39-42](ARCHITECTURE-2026-09-25.md#L39-L42)) смешивает эти два указателя. Нужен явно записанный маршрут: изолированная release-ветка от `74aea456`, публикация её в удалённый `master` после CI, затем перенос четырёх более поздних коммитов на новый tip. При этом два текущих dirty-файла (`AGENTS.md` и старый `STATUS-18-PACKAGES-2026-09-03.md`) нужно сохранить на месте; `reset --hard` в основной рабочей копии недопустим.

### A2. Шаг 0 не сможет получить CI простым push release-ветки

Текущие [tests.yml](../../.github/workflows/tests.yml) и [lint.yml](../../.github/workflows/lint.yml) запускаются по `push` **только для master**, либо по `pull_request`. `workflow_dispatch` планируется лишь в шаге 2 ([архитектура:51-56](ARCHITECTURE-2026-09-25.md#L51-L56)). Значит, шагу 0 до слияния нужен PR в `IvanShift/ruTorrent` или предварительное добавление подходящего триггера; один push отдельной ветки не даёт требуемого «CI зелёный». Это следует и из [официальных правил триггеров GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushbranchesbranches-ignore).

### A3. Не описан триггер немедленной сборки и скрыт старый локальный pin ruTorrent

`docker-rutorrent/.github/workflows/build.yml` запускается по `schedule`, `push` **его собственного** master и `pull_request`; `workflow_dispatch` там нет. Push в `IvanShift/ruTorrent` сам эту сборку не запускает. Если `668846e` не включён и не отправлен, шагу 0 требуется другой явный способ запустить и опубликовать образ; ждать расписания не соответствует оценке 1–2 дня.

Кроме того, `docker-rutorrent/Dockerfile:40` по умолчанию задаёт `RUTORRENT_REF=1fa8defc...`. Только `build.yml:prepare` делает `git ls-remote` опубликованного master и передаёт результат в `build-push-action`. Следовательно, **локальный** `docker build` без `--build-arg RUTORRENT_REF=<новый SHA>` проверит и соберёт старый ruTorrent. Это нужно назвать прямо и в плане шага 0, и в инструкциях по локальной сборке. Выкладку образа с `668846e`, собранного до публикации исправленного ruTorrent, нельзя выполнять как замену шага 0: при запуске она засеет на старом томе политику из старого SHA, которую последующая сборка не перезапишет.

### A4. «Обязательные проверки tests и lint» — не точные имена check-runs

[Публичный API check-runs для последнего зелёного SHA](https://api.github.com/repos/IvanShift/ruTorrent/commits/1fa8defc018bf769dd42147323ab02d460431357/check-runs?per_page=100) возвращает восемь **job**-имён: `php (7.4)`, `php (8.1)`, `jest`, `php-syntax (7.4)`, `php-syntax (8.1)`, `phpstan`, `editorconfig`, `eslint`. Последние два job в `lint.yml` имеют `continue-on-error: true` и сейчас консультативны. Для защиты ветки и проверки из образного workflow надо перечислить шесть блокирующих имён и требовать `conclusion=success` для **этого точного SHA**; проверка «все полученные зелёные» без требования присутствия всех шести даст ложный успех при неполном/пустом списке. GitHub [документирует](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules#troubleshooting-required-status-checks), что контекст required check — имя job, а не имя workflow.

У `build.yml` сейчас `permissions: contents: read`. Публичный [Checks API](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference) удалось читать **без авторизации**. Если реализовывать запрос с токеном, нужно учитывать, что встроенный `GITHUB_TOKEN` docker-репозитория ограничен этим репозиторием; `checks: read` в нём само по себе не выдаёт доступ к другому репозиторию. Настройку защиты `IvanShift/ruTorrent/master` сейчас не удалось подтвердить: публичный запрос к `/branches/master/protection` вернул 401 `Requires authentication`. Это остаётся проверкой владельца, а не доказанным фактом «защита отсутствует». [Область GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/compromised-runners#cross-repository-access).

### A5. Шаг 3 должен менять обе пары tag+SHA, а не только версии в команде

Опубликованный `docker-rutorrent/Dockerfile:27-33` закрепляет **четыре** значения: `LIBTORRENT_BRANCH=v0.16.22`, `LIBTORRENT_VERSION=21a92a...`, `RTORRENT_BRANCH=v0.16.22`, `RTORRENT_VERSION=a8be7e...`. `Dockerfile:85-97` проверяет, что клонированный тег равен заданному SHA, а `build.yml:prepare` читает только `RTORRENT_BRANCH` из Dockerfile и передаёт его в build. Для постоянного обновления образа нужны все четыре значения (`v0.16.24`, libtorrent `90248b01...`, v0.16.24, rtorrent `05cdd03c...`). Временная лабораторная сборка может передать четыре `--build-arg`, но не меняет последующие сборки workflow. Успешность самой сборки и совместимость с плагинами ещё не измерены.

### A6. Критерий `chk-time` несовместим с R1

R1 ([архитектура:238](ARCHITECTURE-2026-09-25.md#L238)) требует: успешный чужой announce означает «не проверять в этом цикле» и **не писать** `d.set_custom`. Текущий fast path, напротив, проходит через `deferVerdict()` → `flushVerdicts()` → `setFastVerdict()` и тем обновляет `chk-time` (`plugins/rutracker_check/updatepass.php:450,650`, `check.php:507-516,545-556`). После предложенного R1 у postponed-строки время закономерно **не** движется в этом цикле. Поэтому условие остановки «`chk-time` у Kinozal, NNMClub и Toloka движется каждый цикл» ([архитектура:245](ARCHITECTURE-2026-09-25.md#L245)) невыполнимо для строк, воспользовавшихся бесплатным проходом. Разделить наблюдение на `checked`, `postponed`, `capped` и задать максимальный допустимый возраст `chk-time`/частоту реальной проверки.

### A7. Последовательность ворот и число выкладок нуждаются в уточнении

Фраза «ворота ставим первыми» ([архитектура:19](ARCHITECTURE-2026-09-25.md#L19)) не совпадает с нумерацией: выкладка шага 0 и три выкладки шага 1 предшествуют либо идут параллельно внедрению ворот в шаге 2. Внутри шага 2 предлагается убрать локальный полный PHP-гейт из hook, заменив его staged `php -l` и Jest, но на время до включения required CI проверок это ослабит реальный предохранитель. Сначала включить/проверить удалённый gate, затем упрощать hook.

Название «три отдельные выкладки» шага 1 тоже не полностью соответствует его содержанию: третий пункт сразу берёт `156c64af`, `af56990f`, `fb0d8711`, `25a0e2cb` ([архитектура:45-49](ARCHITECTURE-2026-09-25.md#L45-L49)). Если это одна выкладка нескольких тем, она расходится с правилом AGENTS.md «one topic, one commit, one deployment». Нужно либо перечислить фактические независимые выкладки и зависимости, либо явно назвать исключение.

### A8. Новые воспроизведения меняют приоритет шага 0 и очередь старого долга

Отдельная [проверка прокси](VERIFY-X-25a0e2cb.md) подняла X3 с P3 до **P2**: Sonarr действительно посылает одиночный `d.views.push_back_unique` с видом `<app>_imported`; rTorrent 0.16.22 принял такую недоверенную команду в лаборатории, а `74aea456` отвечает 403 до демона. Это новая регрессия того самого коммита, который должен ехать в шаге 0. По записанному в AGENTS.md правилу «нет открытого воспроизведённого P1/P2 в дельте» шаг 0 в текущем виде **не проходит собственный критерий выпуска**. Нужно закрыть X3 на release-ветке либо явно изменить границу поддержки внешних клиентов и обосновать это решение до публикации. В том же отчёте проверка смешанного `system.multicall` нашла частичное применение ранних членов перед fault позднего, поэтому предложенную в шаге 4 недоверенную пересылку смешанных пакетов нельзя принимать как уже безопасную модель.

Отдельная [проверка чекера](VERIFY-C-25a0e2cb.md) получила полный живой HTML ответа Tapochek и воспроизвела на поставляемом PHP без `iconv` ложный `CANT_REACH` вместо `DELETED` (**VC-NEW-2, P2**). Это старый код, так что формально не блокирует чужую дельту шага 0, но утверждение ([архитектура:294](ARCHITECTURE-2026-09-25.md#L294)) «шаги 0–3 чинят прод» стало слишком широким. У Tapochek появился подтверждённый реальным ответом отдельный кандидат на раннюю узкую правку; если его откладывают после R1/R2, это должно быть явным решением с датой, а не следствием общего плана переделки.



### A9. Проект банки «по origin» и upstream-обоснование надо уточнить

Отдельная [проверка Snoopy](VERIFY-S-25a0e2cb.md) выявила N-S3/N-S4. Строгая привязка cookie к одному origin из пункта переделки не выражает допустимые `Domain`, `Path` и `Secure` атрибуты; существующий Kinozal-путь `kinozal.guru` → `dl.kinozal.guru` показывает, где такая банка может лишить download нужной cookie. Это **риск предлагаемой реализации**, а не доказанный новый дефект HEAD; нужны захват атрибутов живого Set-Cookie без значений и тест apex→dl до утверждения контракта. Кроме того, актуальный upstream `dropCredentials()` очищает raw `Authorization`, но не raw `Cookie`/`Proxy-Authorization`; при свежем Set-Cookie банка может заполниться снова после `dropCredentials()`. Обоснование в архитектуре о «пустой банке» и снятии всех сырых заголовков нельзя считать установленным для такого перехода. S1 можно также закрыть узкой правкой без немедленной переделки банки; сравнительную оценку этого варианта см. в VERIFY-S.

### A10. Буквальный инвариант R1 запрещает и намеренную запись IGNORED

В [R1](ARCHITECTURE-2026-09-25.md#L238) тест требует «ни одного `d.set_custom` для чужой строки». Но `RuTrackerUpdatePass::run()` проверяет ignore-label до foreign-ветки (`updatepass.php:395–402`): для любой такой строки он откладывает `STE_IGNORED`, затем `flushVerdicts()` записывает его через `setFastVerdict()` (`updatepass.php:576–665`). Это относится и к foreign-строкам; `ruTrackerChecker::run()` при dispatch также записывает `STE_IGNORED` (`check.php:2098–2111`). Нужно выбрать конкретный контракт: либо R1 запрещает **только записи от announce/free-pass** и оставляет IGNORED как явное исключение, либо переводит решение ignore-label к checker и проверяет отсутствие всех записей именно со стороны планировщика. Без такого выбора буквальный тест запрещает существующее намеренное поведение.

### A11. R2 должен отделять чистые решения от исполнителя с гонками и RPC

Формула [R2](ARCHITECTURE-2026-09-25.md#L239-L240) «правила записи `run()` и `flushVerdicts` вынести в чистый модуль» слишком широка. `flushVerdicts()` (`updatepass.php:576–665`) берёт per-hash claims, перечитывает live `d.multicall`, сравнивает snapshot, пишет `setFastVerdict()` и освобождает claims. `ruTrackerChecker::run()` (`check.php:2061–2178`) также перечитывает состояние под claim и принимает решение после результата handler/write. Эти действия не могут стать чистой функцией без потери границы гонки. Чистым слоем могут быть только (1) выбор `skip/dispatch/fast intent` из owner, label, state/msg/time и сигнала, (2) выбор ожидаемого итогового состояния после фактического ответа handler. Отдельный исполнитель обязан повторно проверить live snapshot и результат записи. Таблица `state × msg × time × event` как записана не охватывает owner, label, пропавший hash и отказ записи; эти оси нужно указать в контракте тестов, не обязательно размножая полный декартов продукт.

## Предлагаемая архитектура и порядок поставки

Этот раздел — рекомендации по итогам проверки, а не уже выполненные изменения. С общим выбором исходного плана согласен: точечные переделки сейчас разумнее полной переписи. Дефекты сосредоточены в границах доверия прокси, области cookies, праве планировщика записывать вердикт и проверке выпуска. Оценки сроков и числа будущих находок не служат доказательством этого выбора.

### Прокси: явная политика для пакетов и клиентов

- Решение для отдельного XMLRPC-вызова должно различать локальный `reject`, каноническую доверенную отправку и каноническую недоверенную отправку. В `system.multicall` локальный `reject` любого члена отвергает весь пакет; доверенная отправка допустима, только если доверен каждый член. **Смешанный пакет пока отвергать:** лабораторный rTorrent 0.16.22 применил первый недоверенный член до fault −507 второго ([VERIFY-X](VERIFY-X-25a0e2cb.md)). Однородно недоверенный пакет можно рассматривать отдельно после проверки всех членов на поддерживаемой версии демона и явного описания частичного исполнения. До 0.16.9 `UNTRUSTED_CONNECTION` игнорируется, поэтому там нельзя опираться только на демон.
- Закрыть X3 в том же выпуске, что и `74aea456`: одиночный `d.views.push_back_unique` от Sonarr раньше проходил недоверенно, теперь получает 403, хотя лабораторный демон 0.16.22 его исполняет. Для одиночной команды обратный путь к проверенной недоверенной отправке возможен; переносить его автоматически внутрь доверенного пакета нельзя. Корпус встроенного WebUI должен дополняться отдельными примерами внешних клиентов.
- Корпус запросов составлять из названных действий WebUI через **обе** двери (`httprpc` и `rpc2.php`), записей реальных XML-запросов в лаборатории и известных внешних клиентов. У фикстуры должны быть источник и версия демона: генерация XML только из нынешнего JS может закрепить ту же ошибку, что и реализация. Сближение с upstream оставить целью сопровождения, а необязательный «тонкий режим» отложить до отдельной проверки нового образа и контракта старых демонов. rTorrent 0.16.24 сам по себе не исправляет нынешние 403.

### Snoopy: узкий S1 и полноценная область cookies

- Сначала проверить небольшое исправление S1: анонимный `302 + Set-Cookie` не должен автоматически означать передачу учётных данных чужому хосту. При этом сохранить защиту loginmgr и очистку состояния после отказанного хопа. Это альтернатива предложенному в исходном плане возврату на старый Snoopy с известной LG4 на несколько недель; условия и проба описаны в [VERIFY-S](VERIFY-S-25a0e2cb.md).
- Затем хранить происхождение каждой cookie и применять её `Domain`, `Path` и `Secure` при выборе для следующего хопа. Строгая привязка к origin может сломать допустимый переход `kinozal.guru → dl.kinozal.guru`. Импортировать `Set-Cookie` в контексте ответившего хоста до следующего запроса; отдельно разбирать userinfo, учётные данные аккаунта, анонимные cookies и сырые `Authorization`/`Cookie`/`Proxy-Authorization`. Проверять межхостовые переходы и HTTPS→HTTP, включая `:COOKIE:` и cookies plugin. До утверждения контракта снять у живых ответов только атрибуты `Set-Cookie` и целевые хосты, без значений cookie, и закрепить apex→dl тест.

### rutracker_check: разделить R1, сохранить исполнительную защиту R2

- Первая поставка R1 убирает только запись `UPTODATE` по чужому announce. Для `IGNORED` нужно выбрать явное исключение либо передать решение checker (A10). Пропущенный цикл не меняет `chk-time`; посылка «живой announce означает живую тему» ещё требует измерения. Так убирается спорная запись вердикта без одновременной переделки очереди.
- Вторую поставку с cap начинать, только если нагрузка доказана. Перед лимитом определить точного владельца для обработчиков без `topicPattern` или безопасный fallback: нынешний `ownerOf()` не даёт его для большинства. Для справедливости нужен отдельный `last_attempt` либо вращающийся курсор; сортировка только по старому `chk-time` может отдавать всю квоту одним retryable-строкам. Вместо требования «`chk-time` движется каждый цикл» проверять `eligible`, `dispatched`, `postponed`, `capped` по обработчикам и максимальный возраст последнего настоящего ответа по состояниям (A6).
- Перед R2 утвердить таблицу решений с owner, ignored label, state/msg/time, сигналом и ответом handler. Чистый слой выбирает намерение и переход; отдельный исполнитель под claim перечитывает live state, учитывает исчезнувший hash и результат записи (A11). Подтверждённый реальным HTML P2 Tapochek исправить отдельной ранней правкой, без ожидания R1/R2 ([VERIFY-C](VERIFY-C-25a0e2cb.md)).

### Порядок выпуска и критерии приёмки

1. **Срочный прокси-выпуск:** release-ветка от опубликованной базы с `74aea456`, исправлением X3 и синхронизацией Jest-фикстуры 946. До слияния использовать PR: текущий CI не запускается от обычного push этой ветки (A2). Проверить PHP/Jest и обе двери в rt-lab. Эта ветка может fast-forward удалённый `origin/master`; четыре поздних локальных коммита затем переносятся на новый tip. Текущий локальный `master` от неё fast-forward невозможен (A1). До сборки прочитать наличие политики на продовом conf-томе; собирать образ по точному SHA ruTorrent, поскольку Dockerfile по умолчанию закрепляет старый SHA, а push ruTorrent сам Docker workflow не запускает (A3).
