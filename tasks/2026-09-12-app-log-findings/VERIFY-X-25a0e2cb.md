# Независимая проверка блока X1–X30 и плана прокси, 2026-09-25

Область: `REVIEW-25a0e2cb.md` X1–X30, строки прокси в `CHECK-FIX-CHECK-RECHECK2-5eba5135.md`, разделы «Прокси» и «Шаг 0» в `ARCHITECTURE-2026-09-25.md`. Проверен `master=25a0e2cb`, база `origin/master=1fa8defc`, `upstream/master=fe468360` (совпало с `git ls-remote` 2026-09-25). Исходники rTorrent взяты из локального репозитория с тегами v0.9.0–v0.16.24; тег v0.16.24 сверен с [официальным релизом](https://github.com/rakshasa/rtorrent/releases/tag/v0.16.24). Исходные три файла не менялись.

Методы: прямые вызовы `XMLRPCProxy::decide()` на текущем и базовом файлах; пять узких PHP-наборов (XMLRPCProxyTest, EntrypointTest, ContractTest, PolicyParityTest, RejectionTest), все exit 0; отдельный контейнер `ivanshift/rutorrent:latest` с rTorrent 0.16.22 (удалён после пробы); чтение tagged исходников rTorrent; одна строго читающая проба production httprpc. Никакие пишущие RPC на production не отправлялись. В лаборатории загрузка тестового magnet и проверка view проводились на отдельном контейнере.

**Главное:** X1 подтверждён; X3 имеет более высокий практический приоритет P2, потому что [Sonarr](https://github.com/Sonarr/Sonarr/blob/v5-develop/src/NzbDrone.Core/Download/Clients/rTorrent/RTorrent.cs) вызывает конкретно `PushTorrentUniqueView` с видом `<app>_imported`, а [его RPC-прокси](https://github.com/Sonarr/Sonarr/blob/v5-develop/src/NzbDrone.Core/Download/Clients/rTorrent/RTorrentProxy.cs) отправляет одиночный `d.views.push_back_unique`. В лаборатории rTorrent 0.16.22 такой недоверенный вызов с `myview` вернул 0 и добавил вид; HEAD отвергает его 403 до демона. Это доказанная регрессия поддерживаемого внешнего клиента, но использование Sonarr именно на production здесь не доказано. X5 и X7 подтверждают, что WebUI без httprpc через `rpc2.php` остаётся частично сломанной. X12 следует назвать «недостижимо из WebUI», а не «мёртвый код»: прямые RPC-клиенты могут использовать эти записи.

## Сверка CHECK-FIX по прокси

- **P1 proxy1:** исправление локально работает для пакетов, где *каждый* член проходит повышение. Лабораторный `system.multicall` с недоверенным чтением остаётся 403 (X5), а живой production по-прежнему использует старую политику. Утверждение CHECK-FIX «restoresocketalloc в реальной форме WebUI проходит» некорректно как доказательство живого действия: X12 показывает, что его предшествующий сырой `setsettings` отказывает, когда httprpc выключен, а при httprpc этот JS-путь не вызывается. Пакетный start/stop лабораторно и тестами подтверждён.
- **P2 proxy2:** встроенная и поставляемая политики содержат оба `f.set_*_queued`, а явный старый список может не содержать их. Локальный код доказан; production-исполнение Recreate files не мерилось, поскольку операция записывает состояние. Наличие файла политики на production по HTTP не определено.
- **NEW-1:** локальное `d.multicall2('',main,'d.name=')` проходит; это не означает выкладку. Строго читающая проба 2026-09-25 к живому httprpc дала `system.client_version=0.16.22`, затем `d.multicall2('',main,'d.hash=')` → HTTP 403. Имена или хеши раздач не выводились. Это подтверждает только действующий отказ на живом endpoint, не версию PHP-файла и не содержимое conf-тома.
- **proxy17:** `cat=$d.views=` исправлен, `cat=` старого rTorrent и выражения show_peers_like_wtorrent не исправлены; CHECK-FIX верно ставит «частично».
- **proxy38/39/40:** текущие решения есть; вложенная диагностика system.multicall и подсказки для сохранённого списка остаются отдельными X4/X2.

## Поправки к ARCHITECTURE

1. **Правило пакета нужно написать с тремя исходами.** Если хотя бы один член получил `reject`, отвергнуть весь пакет. Если все получили `send/trusted=true`, послать канонический пакет доверенно. Если все получили `send`, но часть недоверенна, канонически послать без доверия *только при доказанном работающем флаге недоверия демона*; на rTorrent до 0.16.9 заголовок игнорируется. Текст «иначе послать без доверия» сейчас допускает прочтение, будто локальный `reject` тоже превращается в `send`, или будто старая версия сохранит границу. Это опасная неоднозначность [раздела плана](ARCHITECTURE-2026-09-25.md#правило-пакета-общее-для-обеих-копий). Для старого демона безопаснее оставить терминальный отказ для любого смешанного/недоверенного пакета, пока не существует полного локального контракта членов.
2. **Шаг 0 не может fast-forward текущий `master`.** План велит ответвиться от `74aea456`, затем fast-forward `master`; текущий `master=25a0e2cb` уже содержит четыре последующих коммита. `git merge-base --is-ancestor 25a0e2cb 74aea456` вернул 1. Нужен явно описанный staging ref для следующих коммитов и последовательность переигрывания/переноса после первой выкладки, либо отдельная deployment-ветка с изменением целевой ветки. Это новый P3 дефект исполнимости плана.
3. **Проверка Step 0 на production не проверяет P2.** Читающие `d.multicall2` и `system.client_version` различают NEW-1, но не `f.set_create_queued` и не пакетный `system.multicall` записи. Ручной start/stop указан; к нему нужно добавить ручной Recreate files на специально выбранной тестовой раздаче после выкладки или признать P2 проверенным только в лаборатории. До этого не утверждать «P2 измерен на проде».
4. **X3 должен войти в gate шагов 0–1.** В плане выпуск `74aea456` после ревью только ветки system.multicall, но прямые вызовы из того же `$elevate` уже ломают Sonarr. Корпус WebUI не поймает Sonarr; добавьте отдельный контракт валидных одиночных недоверенных вызовов на 0.16.22. Обратный ход для новых `elevate`-методов при несовпадении формы можно возвращать к `send/trusted=false` только поодиночке; внутри доверенного пакета это должно вести к отказу либо к безопасно версионированной недоверенной отправке.
5. **Смешанный пакет без доверия даёт частичное изменение до fault.** На отдельном rTorrent 0.16.22 загрузил тестовый magnet, затем напрямую отправил недоверенный `system.multicall` из `d.views.push_back_unique(hash,partial_view)` и `d.stop(hash)`. Демон вернул результат первого члена 0 и fault −507 второго; последующий `d.views` подтвердил `partial_view`. То есть правило «если не все trusted — отправить весь пакет untrusted» превращает нынешний локальный 403 без побочных действий в HTTP 200 с частично применённым пакетом. Отдельный P2 риск для пакетных действий/клиентов, которые не разбирают вложенные fault. Безопасный вариант: пока смешанный пакет отвергать; пропускать untrusted только если *все* члены дали `send/trusted=false` и каждый способен исполниться под недоверенным соединением, либо явно принять частичную семантику и закрепить её тестом/UX.
6. **Оценки дней и «14 дней без reject» — управленческие критерии, не технические доказательства.** Запросы внешних клиентов могут не появиться за 14 дней, а на production с httprpc raw-список `rpc2.php` не включён. Для покрытия нужен replay реального корпуса по обеим дверям плюс отдельная модель Sonarr/Radarr. Сама идея корпуса хороша, но для записи зафиксируйте источник каждой XML-команды (JS/HTTP-захват/внешний клиент) и ревизию демона.

## Новые находки для общего реестра

- **NEW-X-A · P2 план/покрытие:** выпуск `74aea456` по Step 0 без X3 оставит детерминированный 403 у Sonarr после импорта, хотя старая версия пропускала вызов и rTorrent 0.16.22 его исполняет. Это не новая ошибка кода сверх X3, а пропуск решения в архитектурной последовательности; держать вместе с X3, не считать 126-м независимым дефектом.
- **NEW-X-D · P2 план:** смешанный `system.multicall` после предложенной недоверенной отправки может изменить ранние члены до fault позднего. В лаборатории первый `d.views.push_back_unique` применился, второй `d.stop` дал −507; это проверено по последующему `d.views`. Это не текущая регрессия HEAD: сейчас такой пакет целиком отклоняется до transport.
- **NEW-X-B · P3 план:** невозможный fast-forward из deployment-ветки от `74aea456` в текущий `master=25a0e2cb` (см. поправку 2). Самостоятельная новая находка именно плана.
- **NEW-X-C · P3 план:** проверка после выкладки Step 0 не наблюдает P2 Recreate files (см. поправку 3). Сохранить отдельно как пробел в приёмке.

Прямого доступа к production Docker daemon нет (`docker context ls` показывает только локальный `unix:///var/run/docker.sock`). Достоверная безопасная проверка наличия `conf/xmlrpc_proxy.php` требует читающей команды на production-хосте, например `docker exec rutorrent test -e /config/rutorrent/conf/xmlrpc_proxy.php; echo $?`. Не делать вывод о содержимом конфигурации по HTTP 403 или по версии rTorrent.
