## Выводы, которые меняют решение

Отдельный rTorrent 0.16.22 исполнил эту команду, а [Sonarr действительно отправляет её](https://github.com/Sonarr/Sonarr/blob/v5-develop/src/NzbDrone.Core/Download/Clients/rTorrent/RTorrentProxy.cs). Использование Sonarr на конкретном проде не установлено. По собственному критерию AGENTS.md об отсутствии воспроизведённых P1/P2 в дельте шаг 0 архитектурного плана пока нельзя выпускать без решения X3.
2. **VC-NEW-2 — новый P2 на реально полученном ответе TapochekNet, старый код.** Публичная удалённая тема `https://tapochek.net/viewtopic.php?p=7` ответила 200, `windows-1251`, 11 391 байт, SHA-256 `541b85acf6a7aed472a2a7b070f8806bdd4708a6777fd98c3f46cdba426997ba`. Полный `TapochekNetCheckImpl::download_torrent()` на этом теле возвращает `STE_CANT_REACH_TRACKER=5`, хотя внутреннюю системную таблицу отдельно распознаёт как `STE_DELETED=4`. Вложенная таблица поглощается regex внешней таблицы. В CHECK строка `tests24` правильно отмечает исправление CP1251-байт, но её широкое утверждение «удалённая тема теперь даёт STE_DELETED» на реальной странице неверно. Наличие таких торрентов на продовом экземпляре не установлено.
3. **Первоначальные S1 и X1 подтверждены как P2 в своих условиях.** S1 ломает анонимный переход 302+Set-Cookie на другой хост в неотправленном Snoopy; X1 оставляет старые сырые алиасы записи без защиты на rTorrent 0.9.x, где заголовок недоверенного соединения игнорируется. Из этих двух ни один не доказывает текущую эксплуатацию на измеренном продовом rTorrent 0.16.22. Дополнительно C20 (href AniDUB) и N-S1 (cookie по HTTP) — условные риски раскрытия cookie; нужно подтвердить их реальные предусловия, прежде чем называть инцидентом.

## Что в документах нужно уточнить

- CHECK арифметически корректен, но `checker4` не доказал успешную запись при успешном readback старого того же значения: временный двойник дал вызов handler после отказанной записи. Это **логический контрпример**, не наблюдение такой асимметрии в настоящем SCGI. `tests24` требует указанного выше ограничения. `snoopy22` остаётся регрессом, `consumers9` открытым, `proxy17` частичным.
- REVIEW в большинстве пунктов точно указывает дефект, но S16 как ошибка теста не доказан: shipped-default может быть намеренным контрактом, а локальная правка `conf/config.php` попадает и в экспорт `tasks/matrix.sh`, вопреки тексту пункта. S2 имеет обход кодирования userinfo через `%XX` в другом месте URL; S10 не означает анонимный fetch, если cookies пришли из плагина или `:COOKIE:`. X12 недостижим из WebUI, но доступен прямому RPC-клиенту. O22 — спорное имя, не функциональная проблема.
- Прокси-план нельзя упрощать до «смешанный `system.multicall` послать без доверия»: лабораторный rTorrent 0.16.22 успел применить первый член пакета до fault −507 второго; на 0.16.8 и ниже заголовок недоверия вообще не защищает. Пакетный критерий должен различать локальный reject, целиком trusted и доказанно безопасный untrusted, с явной политикой частичного применения.
- Строгая cookie-банка по origin может нарушить нормальный `Domain=` переход Kinozal `kinozal.guru → dl.kinozal.guru`; нужны Domain/Path/Secure и live capture атрибутов без значений cookie. Актуальный upstream Snoopy не очищает все сырые заголовки авторизации и может снова принять свежую Set-Cookie после drop. Просто скопировать его недостаточно.
- R1 не сможет одновременно пропускать foreign-трекер без записи и требовать изменения `chk-time` **каждый цикл**. Предложенный cap требует определить владельца для обработчиков без `topicPattern` и обеспечить честную очередь: сортировка только по старому `chk-time` может постоянно занимать квоту одними retryable-строками.
- Шаг 0 не может fast-forward **текущий локальный** master от ветки `74aea456`; удалённый `origin/master` fast-forward возможен с последующим переносом четырёх поздних коммитов. До публикации release-ветке нужен PR или новый CI trigger: текущие `tests.yml`/`lint.yml` не запускаются от обычного push не в master. Push ruTorrent не запускает Docker build сам по себе, а локальный Dockerfile по умолчанию всё ещё закрепляет старый SHA. Для официального образа нужен явный запуск build и проверка точного ruTorrent SHA. При переходе на 0.16.24 нужно обновить обе пары tag+SHA для rTorrent и libtorrent; [официальный релиз существует](https://github.com/rakshasa/rtorrent/releases/tag/v0.16.24), но совместимость нового образа не измерена.
- Предлагаемая проверка GitHub check-runs должна требовать шесть точных блокирующих job на одном SHA; «все пришедшие зелёные» может принять пустой ответ. Публичный API доступен без токена; встроенный токен Docker-репозитория не выдаёт доступ к checks другого репозитория просто от добавления `checks: read`. Сначала сделать и испытать удалённый gate, затем упрощать локальный hook.
- Матрица имеет подтверждённые O2–O8: неполный digest, отказ при непроиндексированном удалении, ложный отказ по длине HOME, нога после TERM, иллюзию no-iconv из-за TestLib, зелёный нулевой экспорт и неотозванный last-green. Дополнительно **VO-NEW-1**: при четырёх параллельных прогонах уборка удаляет каталог работающей ноги и даёт ложный `code=99`. Контрпункт: совет CHECK снизить `tmpdir_budget` с 59 до 58 **не обязателен**; адресный SCGITransportTest на TMPDIR ровно 59 дал 134 Passed/0 Failed/0 Notice.
