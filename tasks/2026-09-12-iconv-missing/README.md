# В контейнере нет `iconv()` — что от этого молча деградирует

Обнаружено попутно 2026-09-12, при пробе на проде:
`PHP Fatal error: Call to undefined function iconv()`.
PHP 8.5 в образе `ivanshift/rutorrent` собран **без расширения iconv**.
`mbstring` при этом **есть** (`mb_substr` в тех же пробах отработал).

**Статус 2026-09-25:** пункты 1–2 ниже исправлены в `master` коммитом `af56990f`: маркеры Tapochek и Kinozal проверяются по литеральным UTF-8/CP1251 байтам. Kinozal прошёл 52 теста без ошибок в образе без `iconv`. Дальнейший текст сохраняет исходную диагностику; изменение состава Docker-образа в эту работу не входило.

## Поправка к первому впечатлению

Сначала я сказал, что `plugins/extsearch/engines.php` и
`plugins/rss/rss_reader.php` вызывают `iconv` без guard'а и там fatal. **Это
неверно.** Оба guard'ят вызов и имеют фолбэк на `mb_convert_encoding`, который
в этом контейнере доступен:

- `extsearch/engines.php:127-135` и `:137-145` — `iconv` → `mb_convert_encoding`
  → `utf8_decode`/`utf8_encode`. Работает.
- `rss/rss_reader.php:9-11, 27-36` — `mb_check_encoding` и
  `mb_convert_encoding` пробуются РАНЬШЕ iconv. Работает.

Fatal'ов нет. Остаются два места, где фолбэка на mbstring нет и поведение
тихо отличается от задуманного.

## Что деградировало до исправления

### 1. `trackers/tapocheknet.php:15-23` — **функциональный дефект**

```php
static private function utf8Body($body)
{
    ...
    if (!function_exists('iconv')) return $body;   // <- тело остаётся в cp1251
    $converted = @iconv('CP1251', 'UTF-8//IGNORE', $body);
    ...
}
```

Tapochek отдаёт страницы в windows-1251. Без iconv тело не преобразуется, а
дальше в нём ищется UTF-8-литерал:

```php
const MISSING_MARKER = 'Темы, которую вы запросили, не существует';   // :10
...
if ($text === self::MISSING_MARKER || $text === self::MISSING_MARKER.'.') return true;   // :63
```

В cp1251-теле этот литерал не совпадёт никогда. Значит **определение удалений
для Tapochek на этом контейнере не работает** — удалённая тема читается как
«не смог проверить». Симптома в логе нет: строка просто не появляется.

Ранний выход на строке 18 (`strpos($body, MISSING_MARKER) !== false ||
strpos($body, 'Информация')`) тоже ищет UTF-8 в возможном cp1251 — то есть
и он не срабатывает.

**Проверено ли живьём:** нет. Вывод сделан из чтения кода и измеренного
отсутствия iconv. Нужен прогон по tapochek-торренту, если такие есть во флоте.

### 2. `trackers/kinozal.php:79-92` — мёртвая ветка, последствий нет

`bodyHas()` ищет иглу ещё и в CP1251 через iconv. На проде эта ветка не
исполняется. Последствий нет: `get_srv_details.php` отдаёт UTF-8, и
UTF-8-литерал совпадает. Но ветка выглядит написанной и не работает — а такое
хуже отсутствующей, потому что о ней перестают думать.

Маркер удаления для download-конца, добавленный в той же сессии, эту проблему
уже обходит: он несёт **оба написания литеральными байтами**
(`DOWNLOAD_MISSING_CP1251` / `DOWNLOAD_MISSING_UTF8`), конвертации не требует.
Это и есть образец для остальных.

## Варианты исправления, записанные при обнаружении

1. **Tapochek** — нести маркеры в обоих написаниях литеральными байтами, как
   сделано в `kinozal.php`, и убрать зависимость от конвертации. Либо добавить
   фолбэк на `mb_convert_encoding` в `utf8Body()`.
2. **Kinozal** — то же самое для `GUEST_MARKER` и `MISSING_MARKER`, чтобы
   ветка перестала быть декоративной.
3. Решить отдельно, не стоит ли **добавить iconv в образ**
   (`docker-rutorrent`, пакет `php85-iconv` в Alpine). Это чинит всё разом и
   снимает вопрос, но расширяет образ и не отменяет пункты 1-2 для тех, кто
   собирает иначе.

Пункт 3 и пункты 1-2 не исключают друг друга: код не должен молча зависеть от
наличия расширения, даже если оно есть.
