## S01 — полезное изменение, но часть аргументации неверна

### Подтверждено текущим исполнением

`plugins/rutracker_check/trackers/rutracker.php:743` возвращает CANT_REACH до
`resolveForum()`/`fetchDump()`. Локальный probe исполнил настоящий handler и его
отдельную in-memory копию с **ровно предложенным** изменением decision/confirmed.
В production-файле ничего не менялось.

| Ответ L2 при доступном дампе с absorbed row | Current | In-memory предложение |
|---|---|---|
| -1, 403, 429, 500, 200 с HTML — пять отдельных случаев | CANT_REACH, 1 HTTP, 1 custom read | ABSORBED, 2 HTTP, 2 custom reads |
| Missing row, счётчик уже подтверждён, L2 uncertain | CANT_REACH | DELETED сохранён |
| Missing row, счётчик подтверждён, cap=0 | DELETED сохранён | Контроль нынешней skipped-ветви |
| Missing row, нового подтверждения нет, L2 uncertain | — | CANT_REACH, **не** DELETED |

Это доказывает выбор ветвей и отсутствие нового deletion confirmation в данном
контрольном сценарии. Не заменяет полную матрицу неизвестного/испорченного counter,
failed read/reset, нового healthy stamp и всех dump statuses. Полный реальный
BEP-9 replacement в этой проверке не запускался: positive dump branch проверен
на ABSORBED, а proposed updated branch трассируется в тот же switch и `begin()`.

**Тест №13 действительно слабый.** Исполнен именно callback из текущего
`RuTrackerHandlerTest.php:932`, не его пересказ: он PASS и с настоящим handler,
и с изменённой in-memory копией. Без queued `chk-forum` вариант достигает чтения
форума, получает unreadable и выходит. Обе версии имеют один HTTP и тот же result;
число custom reads различается (1 против 2). Значит assertion «layer 3 never reached»
не доказывает написанное. Это полноценный пробел теста при **обоих** контрактах.

### Что опровергнуто или преувеличено

1. **«Проза плана не называет uncertain» — опровергнуто.**
   [План, Task 11](../plan-rutracker-check-post-api.md:1623) прямо задаёт
   `uncertain → STE_CANT_REACH_TRACKER`; reference implementation повторяет это
   на строке 1684. Сам анализ сначала правильно цитирует это, затем отрицает.
   [Дизайн §4.3](../design-rutracker-check-post-api.md:437) определяет классификацию
   уже полученного dump, но не говорит однозначно, что dump обязан запрашиваться
   после любого uncertain L2. Таблица downstream verdicts не отменяет upstream gate.
   Функциональное обоснование изменения убедительно; доказательства «решение никогда
   не принималось / никакого изменения контракта нет» — нет.
2. **«Это новое следствие, которого нет в реестре» — опровергнуто.**
   Прежний отдельный A/J/K/M/O audit уже описывает K4: counter/message не меняются,
   outer checker state меняется. Сводный S01/K4 различает его с M06 (проба вообще
   не отправлена). Нельзя считать новый дубль отдельным discovery.
3. **10 отказов / 6 поздних updated / 44 skips подтверждены пересчётом лога**,
   но из более позднего updated нельзя доказать наличие тех же bytes в dump
   **на момент более раннего 403**. Для этого нет contemporaneous dump capture.
   Четыре пары имеют поздний updated без промежуточного forum-unknown; две — с ним.
   Это согласуется с задержкой обнаружения, не измеряет точный counterfactual выигрыш
   «в шести случаях замена уже ждала». Один промежуток вообще охватывает десять часов
   без следующего scheduled check; все эти часы нельзя приписать одному раннему return.
4. **«≤2 дополнительных GET / цикл на этом парке» не установлено** имеющимися
   classified строками. Memo ограничен процессом; cap — на host/window и настраиваемый,
   не глобально 10 на всю установку. Несколько hosts/manual процессов дают другую
   границу, а cold cache не обязан отвечать 304. Дополнительная нагрузка вероятно
   умеренная, но число и долю трафика нельзя объявлять измеренным свойством patch.
5. **«403 задерживает ровно один цикл» — условно.** Следующая проверка пройдёт L2
   как skipped, только если cooldown ещё активен; после длительного перерыва может
   прийти новый 403. Unknown forum, Layer1/fuse, недоступный dump и metadata wait
   независимо могут задержать результат. «После UA все 403 прекратятся, останутся
   только таймауты» — прогноз, не установленный результат текущего deployment.

### Рекомендованный контракт

- `registered` сохраняет нынешний положительный early return; `unregistered`
  остаётся единственным L2 основанием выставить `trackerConfirmed=true`.
- `uncertain` допускает L3, но сохраняет `trackerConfirmed=false`.
- Валидная положительная строка dump может дать updated/closed/absorbed/uptodate.
- Missing row не создаёт нового DELETED без независимого tracker confirmation.
  Сохранение **прежнего** DELETED допустимо только после текущей проверки missing
  row и валидного не-прерванного counter, включая chk-stime. Не сохранять его
  слепо по старому UI state и не обходить unreadable/failed-write gates.
- Если dump недоступен или неоднозначен, остаётся retryable CANT_REACH.
- Обновить комментарии у обоих gates: «проба не выполнялась» станет неточным для
  inconclusive. Нынешняя строка `probe budget is spent` тоже не объяснит actual
  timeout/HTML. Отдельный `inconclusive` verdict/diagnostic полезнее семантической
  подмены на cap/cooldown.

Сначала переписать тест №13 с настоящим доступным forum/dump и зафиксировать
старый RED для нового контракта; затем positive statuses + missing/deletion
negative controls + budget/failed dump/failed reset cases. GREEN 743 старых тестов
не является доказательством безопасности изменения, если проверяемый gate в них
вообще не различим. Это следующий change task, не уже выполненное исправление.

## S02 — исправлять ошибочную конфигурацию, не угадывать смысл чисел

### Что измерено заново

`forumindex.php:1072`: `max(0, (int) configured)` при isset, default 86400 иначе.

| Настройка | Actual cooldown | claims в T / T / T+1 |
|---|---:|---|
| null / default | 86400 | true / false / false |
| `''`, false, `'abc'` | 0 | true / false / true |
| явные 0 / `'0'` | 0 | true / false / true |
| 24 | 24 | true / false / false |
| 3600 / 86400 | исходное число | true / false / false |

Ноль разрешает новые окна в **разных секундах**, не вообще каждый одновременный
вызов. Между callers нет mutex на длительность всего crawl; один час cooldown
тоже не запрещает overlap, если реальный crawl идёт дольше часа. Нагрузка при
unresolved topics реальна, но постоянный full sweep требует сохранения этих
условий; раннее разрешение wanted или отказ прекращают обход раньше.

### Ошибки аргументации и оценки

- Git подтверждает добавление `>=0` в `29be3350`, но это **не чисто документный
  commit**, а большой remediation. Поздний `35e5cb38` тоже содержит рабочие правки.
  История аннотации не доказывает психологическое намерение автора или отсутствие
  пользователей настройки. Текущее документированное поведение — compatibility
  fact, даже если исходный design умолчал о нуле.
- 1261 forum / 140 sampled forums / 50.4 MB — **историческая выборка дизайна**,
  не сегодняшний capture и не каждый full crawl. `~450 MB` — экстраполяция
  распакованных данных, не объём сетевого трафика. `~1 hour` — оценка, не новый
  benchmark. 404/410, размер dump, cache и ранний выход меняют стоимость.
  Менять приблизительное `~1500` на безусловную точную константу 1261 тоже неверно:
  лучше «число форумов текущего дерева» и дата/условия historical measurement.
- 24 seconds — маленькая **валидная** длительность, не доказанная опечатка
  «имелись в виду часы». Пол 3600 меняет её смысл, как и смысл явного 0.
  Поэтому это не «две строки почти только документации».
- При сохранении нуля исключением clamp сам по себе не лечит мусор: после `(int)`
  отличить `'abc'` от намеренного 0 уже нельзя. Сначала нужна валидация raw input.
- Не все соседние invalid configs равно безопасны: например, снижение fuse floor
  до 1 повышает частоту отсечения кандидатов. Общая фраза про «все безопасны» не
  заменяет собственный домен и последствия конкретной настройки.

### Рекомендация

**Исправить в отдельном небольшом задании**: принимать явно определённый числовой
домен; пустую строку, boolean, нечисловой мусор и прочие невалидные типы не обращать
в «без ограничений». Разумный fallback — shipped 86400 с classified предупреждением
о названии настройки/использованном default, без печати произвольного raw value.

**Пока сохранить** явные canonical 0 и допустимые positive values, документируя
секунды, реальный смысл нуля и возможность дорогого обхода. Если владелец хочет
запретить zero/small values — отдельно утвердить минимум и migration semantics.
Если задача именно исключить одновременные обходы, нужен review whole-crawl lock
до захвата/потребления queue; произвольный minimum delay не является его заменой.

Приоритет ниже S01 и ниже safety/приёмочных блокеров №6. Существование аварии на
живом deployment этим аудитом не установлено; отсутствие настройки в логе тоже
не доказывает, что никто никогда её не задавал.

## S03 — сохранить нынешнюю политику

### Подтверждено

Новый probe над current `RuTrackerAnnounce`:

- три reservations до первого ответа → allow/allow/allow;
- три последующих 403 → 3600 / 7200 / 14400;
- последовательный reserve→reply loop из десяти попыток отправляет только один
  запрос, остальные видят cooldown;
- 200 внутри active cooldown не меняет состояние; 200 после истечения сбрасывает;
- 429/500/-1 не изменяют outcome record.

Current handler sequential; aggregate scenario требует overlapped callers
на разных hashes/claims. Два клика по **одному** torrent не гарантируют две probes:
`check.php:1984` имеет per-hash claim. Sequential in-process форма нескольких
403 во время того же active cooldown через штатный loop недостижима, но сама
public recordOutcome принимает последовательные replies ранее зарезервированных
конкурентных запросов — именно это моделирует синтетическая последовательность.

### Что следует исправить в анализе, не в backoff

1. «Первый 403 прекращает цикл» в design — operational rule для последовательного
   потока, **не определение общего cycle ID** между scheduler и несколькими manual
   processes. Текст не задаёт membership/начало/конец общего refusal round.
   [План Task 3](../plan-rutracker-check-post-api.md:277) прямо задаёт doubling на
   каждый 403. Старый осторожный вердикт S03 был обоснован.
2. Лог не содержит пары concurrent 403 одного host, но не доказывает отсутствие
   overlap вообще. Редкие timestamps без сохранённого cooldown state/полного
   traffic capture не устанавливают ни точный prior ceiling, ни UA как единственную
   причину достижения потолка. Последовательные refusals достаточно объясняют
   такой backoff, но это inference.
3. «Самоизлечивается на следующем 200» — только после истечения active cooldown.
   Иначе это противоречит собственному верно выполненному probe №5.
4. **Новые persisted generations не обязательны.** Сам анализ в конце предлагает
   coalescing during active cooldown без нового поля. Это допустимый альтернативный
   дизайн, но поздний 403 — отдельный HTTP-ответ, а не доказанно тот же ответ дважды.
   Считать его частью прежнего cooldown — выбор политики, не обнаружение duplicate.
5. Называть дополнительные 1–3 часа «шумом» нельзя для всех пользователей. Это
   реальный trade-off задержки и снижения запросов, просто ограниченный по эффекту
   и не дающий подтверждённого ущерба payload. L3 после budget skip может работать;
   его дальнейшие ошибки/неизвестный forum не исчезают автоматически.

**Рекомендация: сейчас не менять S03.** Сначала S01 убирает зависимость положительных
dump verdicts от неопределённого announce. Коалесцировать late 403 имеет смысл
только при подтверждённой практической потребности в более быстром восстановлении
и явном решении о политике. Если оно будет принято, проверить несколько разных
hashes, boundary now==until, later failure и late success — без выдуманного
идентификатора раунда из текста дизайна.
